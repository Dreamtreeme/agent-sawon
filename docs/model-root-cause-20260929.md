# 반복 오류 원인 진단 — 2026-09-29

후속 구현과 실측은 [응답 계약·무진행 복구 수정 기록](contract-repair-20260929.md)에 기록한다.
아래 내용은 수정 전 진단을 보존한 것이다.

현재 경량 모델의 최종 조회 실패에는 실행 로직의 문제가 있다. 마지막 실패 요청을
복원해 실측한 결과, 현재 단계와 다음 단계가 섞인 지침 및 API 응답 스키마와 Python
검증기의 불일치가 확인됐다. 모델을 상위로 바꾸거나 동일 화면 실행을 반복하는 것만으로
이 계약 문제가 해결되지는 않는다. 이번 작업에서는 운영 코드와 가드를 변경하지 않았다.

  버전이 달랐던 실행을 같은 코드의 성공률로 합산하지 않는다.
- 총 모델 호출 141회 중 137회 응답 검증 통과, 4회 로컬 ValidationError,
  HTTP/503 오류 0회였다. 전체 업무 완료는 5건 모두 실패했다.
- 마지막 실행 `20260928T235735Z-30baad6d`에는 전경 이탈도 없었다.
  저장 후 조회값 입력과 창 확장까지 했지만 필수 검색 전에 응답 검증이 두 번 실패했다.
- 이전 503, 이전 실행의 전경 이탈은 각각 실제 별도 오류다. 다만 최신 실패를
  그 원인으로 설명할 근거는 없다. 관찰 중 COMError 경고와 응답 검증 실패의
  인과관계도 확인되지 않았다.

## 1. 모델에 보이는 스키마와 실제 검증 규칙이 다르다

`brain/graph/schemas.py`의 `Decision.require_consistent_operation`은 Python
사후 검증기로 operation/intent/action의 조합을 검사한다. 이 교차 필드 제약은
`model_json_schema()`에 구조적 제약으로 포함되지 않는다.

`FinalQueryPendingDecision`은 operation만 act/stop으로 제한한다. intent에는 verify,
action에는 null, evidence에는 완료 근거 목록이 여전히 허용된다. 새 실측에서
반복된 응답은 `operation=stop, intent=verify, action=null, evidence=11개`였다.
개별 필드의 JSON 스키마에는 맞지만 Python의 `nonaction_intent_mismatch` 규칙에 걸린다.

검증기만 제외하고 동일 필드·설정·설명으로 동적 모델을 만들었다. 내보낸 JSON 스키마가
완전히 같음을 assert한 뒤 같은 새 응답을 검증하면, 동적 모델은 통과하고 운영 모델은
실패한다. 독립 jsonschema 라이브러리로 검증한 결과라고 주장하지 않는다.
이 실험은 내보내는 스키마에 사후 검증 규칙이 표현되지 않는다는 증거다.

## 2. 검색 대기 단계에도 완료 응답 지침을 보낸다

`brain/graph/engine.py`의 `FINAL_QUERY_GUIDANCE`는 저장 확인, 조회 화면 이동,
조회값 입력, 검색, 최종 근거 제출을 한꺼번에 설명하며 `complete/verify/null` 예시를
포함한다. 이 전체 지침은 검색 대기 단계의 `phase_instruction`에도 들어간다.
동시에 pending 스키마는 complete를 금지한다. 순서를 끝까지 해석하면 수행 가능하지만,
현재 응답에서 해야 할 일과 미래의 완료 형식이 혼재한다.

마지막 요청의 실제 상태는 다음과 같다.

```text
phase=final_query
query_value_verified=true
query_submitted=false
next_required_step=search
```

이미 화면에 결과 행이 있어도 아직 검색 행동을 해야 한다. 원문 재현 응답은
그 행동 대신 완료 근거를 stop/verify 형태로 제출했다.

## 3. 제한된 A/B 실측으로 단계 지침의 영향을 확인했다

저장된 관찰과 정상 결정을 재생해 마지막 GUI 실행의 요청 해시 28개를 모두 일치시켰다.
실패 호출은 운영 코드가 받는 ValidationError 전환을 재현했다. 원래 잘못된 모델
응답은 저장되지 않았으므로 복구하거나 내용을 추정한 것은 아니다.

최종 요청 SHA-256:
`5fbaf038bad8d6f9dde545868f1e91b786f948f85d953c37be3377a584dfe0cd`.

먼저 원문 1회를 새로 호출하고, 이어 원문/집중 지침/원문/집중 지침/집중 지침 순서로
5회를 호출했다. 모델은 모두 `gemini-3.5-flash-lite`다. 집중 지침은
`phase_instruction`과 `final_query_required`의 `required_response`만 현재 검색
단계로 좁혔다. 모델, 응답 스키마, 관찰, 레코드, 계획, 상태 플래그,
`next_required_step`, 공통 POLICY는 동일하다. 특정 ERP 라벨·ref·경로를 지침에
주입하지 않았다.

| 조건 | 호출 | 로컬 응답 검증 | 반환한 동작 | 비용 합계 |
| --- | ---: | ---: | --- | ---: |
| 기존 지침 | 3 | 0/3 | stop + verify + null, 근거 11개 | $0.00771874 |
| 현재 검색 단계만 안내 | 3 | 3/3 | act + search + 현재 관찰의 검색 버튼 click | $0.00481552 |

모든 호출은 ModelClient를 거쳤고 SDK 자동 재시도 없이 토큰·지연·비용을 기록했다.
추가 6회 확인 가능한 비용은 **$0.01253426**, 미확정 비용과 HTTP 오류는 없다.
단가 계산에는 반환된 캐시 토큰 사용량도 반영되므로 입력 토큰 수만으로 비용을
재계산하지 않는다. 처음 발생한 동적 모델 구성 assert 실패는 API 호출 전이며
측정 6회에 포함하지 않는다.

이 결과는 해당 저장 상태에서 현재 단계 지침이 실패에 기여함을 뒷받침한다.
모든 스키마 문제를 해결했다거나 전체 GUI 작업을 통과했다는 결과는 아니다.
실제 클릭은 실행하지 않았으며, 작은 표본·하나의 관찰 상태에 대한 진단이다.
원문 당시 두 실패 응답이 새 재현 응답과 같았다고 단정하지 않는다.

## 4. 재시도와 진행 판정에도 결함이 있다

- `_select_node`는 ValidationError의 구체적 규칙을 잃고
  `final_query_required`로 묶는다. `_fail`은 같은 전체 최종 조회 지침을 다시 보내므로
  무엇을 고쳐야 하는지 명확하지 않다. ModelClient 로그에도 오류 종류만 있고
  안전하게 정제한 필드 경로·검증 규칙이 없어 사후 진단이 늦어진다.
- 별도 실행 `20260928T235301Z-cced547f`는 조회 이동을 주장하면서 같은 시스템 메뉴를
  8회 선택했다. 첫 7회 relay 응답은 ok였지만 활성 창은 같았고, 반복 2–7회의
  screen_hash도 같았다. `_verify_node`는 관찰 가능한 이동이 없어도 해당 행동의
  `ok:true`와 모델의 subgoal을 피드백에 넣는다.
- `_record_progress`는 새 창에 대해서만 실패 연속 횟수를 초기화하지만, 진행 없는
  탐색 자체를 실패로 세지는 않는다. 따라서 같은 선택을 총 step 한도까지 반복할 수
  있다. 이 문제는 반복 동작을 설명하지만, 최신 ValidationError의 직접 원인과는 별개다.
- 무한한 프롬프트 증가를 원인으로 볼 근거는 없다. 피드백은 최근 12개로 제한되며
  위 메뉴 반복 구간의 입력 토큰은 6,204에서 6,166으로 감소했다.

## 수정 우선순위 — 아직 운영 코드에 적용하지 않음

1. 현재 단계별 허용 행동과 지침을 일치시킨다. 검색 전에는 검색 등 필요한 현재
   행동 계약만 제공하고, 검색 후에 최종 근거 제출 계약으로 전환한다.
2. operation별 유효 조합을 내보내는 스키마에도 표현한다. 단순 설명문 추가가 아니라
   모델이 받는 구조적 계약과 Python 검증의 일치를 확인한다. 잘못된 응답을 임의로
   정상 응답으로 변환하거나 기존 완료 검증을 약화하지 않는다.
3. 검증 실패를 허용된 규칙명·필드 경로로 정제해 기록하고, 그 위반과 현재 단계에 맞는
   보완 요청을 보낸다. 원문 응답·프롬프트·비밀값은 공개 기록에 넣지 않는다.
4. 행동 전달 성공과 목적 달성을 구분한다. 관찰 가능한 변화 없는 반복 탐색은
   제한된 복구 또는 중단으로 이어지게 한다. 화면 해시 하나만으로 성공을 판정하지 않는다.
5. 내보낸 스키마와 로컬 검증의 일치, 무진행 반복을 회귀 검증하고, 저장 요청 재현
   실측을 거쳐 경량 모델 전체 GUI 흐름을 새 실행으로 검증한다.

기존 152개 테스트는 스크립트 응답에 대한 가드와 상태 전환을 검증한다. 실제 모델이
전송된 계약을 일관되게 해석함을 증명하지 않는다. 이번에는 운영 코드 변경이 없어
전체 테스트를 다시 돌리지 않았으며 기존 통과 결과를 새 GUI 성공으로 해석하지 않는다.
