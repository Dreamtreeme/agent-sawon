요청했다. L2C의 현재 코드·테스트·실패 기록을 읽고 Sawon과 비교했다. 조사 시 L2C
HEAD는 `db144a6`이며 추적 파일 변경은 없었다. L2C를 수정하거나 실행하지 않았고
API·GUI·계정 정보·실제 수집 데이터는 사용하지 않았다. 문서의 옛 계획은 현재 구현과
구분했다. 이 문서는 적용 제안이며 새로운 구현이나 GUI 성공을 뜻하지 않는다.

핵심 교훈은 실행기가 이미 확인한 사실을 관리하고, 모델에게 현재 화면의 미해결
선택만 맡기는 것이다. Sawon의 관찰→선택→실행→검증 구조와 안전 가드는 유지한다.
오류가 나올 때마다 공통 프롬프트에 예외를 추가하기보다, 한 상태 정책에서 모델의
선택 범위와 실행 검증을 함께 만들어야 한다.

## Sawon에서 이미 고친 것과 남은 것

직전 수정으로 외부 응답 계약, const→enum, 현재 단계 지침, 안전한 검증 오류 피드백,
동일 화면 무효 탐색 차단, 자격증명 입력 전달 기억을 구현했다. `ruff check`,
`ruff format --check`, 전체 `pytest` **237개 통과(108.31초)**를 확인했다.
이는 실제 경량 GUI 전체 성공을 증명하지 않는다.

- **선택지 제한은 아직 부분적이다.** `engine.py:_decision_schema`는 중복 근거와
  최종 조회를 구분하지만, `WireActDecision`의 intent·action·source 조합은 넓다.
  로그인 입력을 마친 상태에서도 모델은 재입력 응답을 만들고 실행 가드에서 거절될 수
  있다. 입력 제출 사실에서 같은 정책으로 스키마·지침·가드를 만들면 이 불일치를 줄인다.
- **전이 판정은 행동 종류마다 다르다.** 입력은 값 재확인, 탐색은 의미적 화면 변화,
  비밀번호는 보호 컨트롤 재확인이다. 후자의 `ok`는 비밀번호 값이나 인증 성공이 아니다.
  현재 추가된 제출 기억은 옳은 방향이며, 이 차이를 공통의 명시적 결과 계약으로 정리한다.
- **왕복 반복은 별도 빈틈이다.** `_verify_node`는 A→B와 B→A를 모두 화면 변화로
  인정한다. `_record_progress`가 같은 상태를 새 진행으로 다시 세지 않아도, 변화 있는
  행동 자체를 실패로 세지는 않으므로 업무 진전 없는 왕복은 단계 한도까지 갈 수 있다.
  이는 코드 경로에서 도출한 위험이며 새 GUI에서 재현한 결과는 아니다.
- **완료 가드는 유지해야 한다.** `_check_complete`는 저장 후 새 검색과 동일 결과 행의
  모든 필드 근거를 요구한다. DB 10/10과 `awaiting_approval` 도달은 별도 지표다.
  L2C의 화면 전이 성공이나 캐시 재생 성공으로 이 계약을 대체하지 않는다.

## 다음 구현 순서와 통과 조건

1. **현재 상태 계약을 한 곳으로 모은다.** `current_step`, `verified_facts`,
   `pending_effect`, `blocked_repeats`를 타입이 있는 실행별 상태로 정의한다. 우선 현재
   필드에서 정책 스냅샷을 도출하고 그래프 전체를 재작성하지 않는다. 같은 사실을 여러
   bool·프롬프트 분기에 독립 저장하지 않도록 갱신 소유권과 무효화 조건을 지정한다.
   입력 전달/값 확인/인증 확인/저장 요청/조회 완료를 서로 승격하지 않는 테스트가 기준이다.
2. **하나의 정책에서 선택지·응답 스키마·실행 가드를 만든다.** 남은 입력 source만
   허용하고, 저장 전에는 저장 전제조건을, 완료 전에는 조회 근거 전제조건을 적용한다.
   현재 관찰에 근거한 탐색·제한된 대기·중단은 필요한 상태에서 유지한다. 화면 종류는
   모델 주장만으로 확정하지 않고 관찰 근거와 함께 검사한다. 금지 행동은 모델 계약과
   실행기 양쪽에서 막히며, 제공자용 enum 변환과 비용 계측이 유지돼야 한다.
3. **행동 효과와 순환을 검증한다.** 실행 전후 관찰 ID, 행동, 기대 효과, 전달 결과,
   관찰된 효과, 새 업무 근거를 한 전이로 연결한다. 같은 입력 반복·무효 클릭·A–B–A–B를
   구분하고, 업무 근거가 늘지 않는 반복은 기존 실패 한도 안에서 대안 또는 중단으로
   처리한다. 정상적인 목록 복귀나 다른 필드 입력을 순환으로 오인하지 않는지도 검증한다.
4. **실패 묶음을 먼저 재생한다.** 비밀번호 비노출/입력 반복, 무효 메뉴, 왕복 탐색,
   오래된 ref, 중복 근거 누락, 저장 후 검색 생략, DB 저장 성공이지만 조회 검증 실패를
   fake/replay에서 확인한다. 금지 요청이 relay에 실제 전달되지 않았는지 검증한다.
   기존 237개를 다시 만드는 대신 빠진 계약 사례만 추가한다.
5. **그 뒤 동일 코드의 GUI 한 건으로 확인한다.** 저장 관찰의 모델 단건 통과와 실제
   전체 실행을 구분한다. 경량 단독 조건을 유지하고 최종 필드 근거·내부 성공 상태·
   `awaiting_approval`까지 모두 확인한다. 실패 시 해당 전이부터 원인을 분리하고
   전체 재실행부터 반복하지 않는다. 통과 후 같은 코드 반복·요약 전략·개발 시드 비교로
   확장한다. 비용·단계·실패 상한과 D3/D4/D5의 제안 상태는 변경하지 않는다.

## 그대로 가져오지 않을 것

L2C는 로그인·CAPTCHA를 자동화하지 않는다. 공개 검색어 제출 기억은 참고할 수 있지만
비밀번호 문제를 이미 해결한 선례는 아니다. 비밀번호 원문이나 값 검증을 로그에 넣지 않는다.

사이트 프로필, 자동 Enter, 뒤로가기→탭 닫기의 고정 경로, 좌표·ROI 재생은 ERP에
복사하지 않는다. 특히 영속 경험 캐시·Critic 승격은 Sawon의 M2 범위다. M1에서 필요한
실행 중 기억과 회귀 fixture는 성공 경로를 이후 실행에 재생하는 캐시와 구분한다.

L2C의 function calling 전체 전환이나 const 사용도 채택할 이유가 없다. 현재 Sawon의
const→enum 개선은 동일 조건 단건 실측 근거가 있으므로 유지한다. 상위 모델 복구는
별도 실험 조건으로 두며 경량 단독 성공률에 섞지 않는다.

L2C도 [자체 기록](../../../L2C/docs/evidence/l2c_metrics_20260822.md)에 후보 재진입 반복과
자동 검사/사람 필드 감사의 차이를 남겼다. 완성된 만능 해법으로 보지 않는다. 화면 안정화는
참고할 별도 계약이지만, 이번 최근 실패의 원인이라고 확인된 것은 아니다. 개선할 경우에도
core는 relay 관찰만 사용하며 UIA 우선 원칙과 ERP 내부 접근 금지를 지킨다.
