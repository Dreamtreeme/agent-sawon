# 실제 앱 업무 완수와 경험 재사용 계획

기준일: 2026-11-09. 상태: B0·X1·X2·I1 완료. X2는 기존 Calc 창을 프로젝트가 선택해
파일 열기·입력·저장·정상 종료한 조건이다. 전체 업무의 구현 완료를 뜻하지 않는다.
운영값은 [현행 런타임](current-runtime.md), 코드·계약 소유권은 [계약 지도](contracts.md)를 따른다.
이 계획은 앞선 17단위 계획의 우선순위를 대체한다. 이전 문서는 날짜별 아카이브에 보존한다.

## 큰 목표

사용자가 업무 매뉴얼과 자료 위치를 알려주면, 기존 Windows 프로그램에서 정보를 찾아
다른 프로그램에 처리하고 결과를 확인한다. 성공한 방법을 새로운 자료에 재사용하여
사람의 교육·개입·검수·재처리 부담을 줄인다.

## 목표 난이도와 최소·최대 목표

최소 목표는 **사용자가 명시한 GUI 업무 하나를 여러 앱에서 정확히 완료하는 작업자**다.
최대 목표는 **여러 업무 중 새 정보를 해석하여 기존 업무의 변경·새 업무·참고 정보를 구분하고,
필요한 대상을 찾아 처리하며 중단한 업무까지 이어가는 에이전트**다. 최대 목표의 첫 검증은
교육된 업무군과 등록 앱 안에서 수행한다. 모든 사무 업무에 대한 일반 지능을 완료 조건으로
삼지 않는다. 아래 단계는 기능·평가의 범위이며 런타임에 강제할 상태 기계나 거절 규칙이 아니다.

| 단계 | 목표와 난이도 | 관찰 가능한 통과 조건 | 현재 근거 |
|---|---|---|---|
| L1 화면 조작 | 한 화면에서 읽기·클릭·입력·스크롤 | 모델이 고른 대상과 실제 전달·변경 결과가 일치 | 기존 ERP·앱 실행에 근거 있음 |
| L2 한 앱 업무 | 파일·자료를 찾아 입력·저장까지 완료 | 지시한 대상을 선택하고 최종 산출물에 요청한 변경만 반영, 작업자 정상 종료 | X2의 지정 시험 복사본 열기·입력·저장 조건에서 확인 |
| **L3 명시 업무 완수 — 최소 목표** | 자료 위치·목표·완료 조건을 받아 앱 간 업무 하나를 수행 | 원본을 직접 찾아 필요한 값을 모으고 정확한 출력 대상에 반영. 정답·좌표의 사전 주입과 실행 중 사람의 업무 개입 없이 완료 | I1은 수량 하나 연결의 성공 근거. 전체 주문 S1과 변형 반복 검증은 미완료 |
| L4 경험 재사용 | 성공 방법을 새 자료에 적용 | 이전 값을 복사하지 않고 새 값을 읽어 같은 방법으로 완료. 미결합·복구·사람 개입과 시간·비용을 함께 측정 | 기존 Mock ERP 근거와 실제 앱 새 자료 재사용을 구분. C0→C1→R1 이후 확인 |
| L5 업무 맥락 유지 | 중단·다른 화면·정정 정보가 있는 동일 업무를 이어감 | 원본 값·출처·처리 대상·확인된 진도·남은 일을 연결. 새 정정을 맞는 업무에 반영하고 이전 진도로 복귀 | 정적 값 누적·출처·후속 입력은 확인. 중단·정정·유사 대상의 반복 검증은 미완료 |
| **L6 업무 맥락 조립 — 최대 목표** | 여러 업무 중 새 정보를 찾아 업무를 생성·갱신·선택·재개 | 같은 주문의 수정과 별도 주문을 구분하고 필요한 메일·대화를 추적. 불명확한 부분은 필요한 질문으로 해소하며 업무를 섞지 않고 완료 | 확장 목표. 새 정보로 업무 생성·선택하는 경계는 현재 구현 완료로 세지 않음 |

L4는 재사용·경제성의 평가 축이며 L5·L6의 맥락 판단을 가능하게 하는 필수 선행조건은 아니다.
탐색과 기억인출은 기존 공통 GUI 실행 경로를 유지한다. 새 정보의 의미 판단까지 과거 경로로
고정하지 않으며, 편찬·인출의 호출 0회를 최소·최대 목표의 통과 조건으로 쓰지 않는다.

### 최소 목표의 평가 범위

- 업무 유형: 자료 검색·확인, 한 앱의 작성·수정, 앱 간 정보 반영. 첫 대상은 기존 S1
  Gmail·카톡→Calc이며, 이 업무만으로 범용 GUI 에이전트와 동급이라고 주장하지 않는다.
- 정답 업무 값·클릭 좌표·정답 행동 순서는 작업자에 주지 않는다. 사용자의 매뉴얼·자료
  위치·앱·완료 조건은 허용한다. 대상 본문이나 출력 파일을 사람이 미리 열었다면 별도 조건이다.
- 값 변경, 같은 이름의 다른 파일·대화, 기존 앱·문서가 열려 있는 시작, 부분 화면·스크롤을
  선정 과제에 포함한다. 올바른 대상에만 쓰는 것은 최소 목표부터 요구한다.
- 초기 내부 게이트는 사전에 고정한 10개 시나리오 × 3회 = 30회 중 독립 업무 성공 24회 이상,
  다른 대상의 실제 변경 0회로 둔다. 이는 개발용 목표이며 시장 표준이나 통계적 동등성의
  증명은 아니다. 실패·중단·재시도도 분모와 비용에 남긴다.
- 외부 동급 비교는 레퍼런스 GUI 에이전트 한 개의 버전·모델·도구·시간/단계/비용 한도를
  고정하고 동일 과제·시작 상태·정답 평가·반복으로 수행한다. 선택된 과제에서 관측한 성공률이
  동등 이상인지 확인하고 사람 개입·비용·시간을 함께 보고한다. 비교 실행 전에는 동급 미검증이다.

### 최대 목표의 평가 범위

합성 주문 두 건 A/B를 두고 다음 여섯 상황을 사전에 준비한다: A 처리 중 B 알림으로 전환,
A의 수량 정정, 같은 이름의 다른 문서·대화, 두 출처의 값 충돌, 이전 업무 재개, 기존 업무와
무관한 새 요청. 필요한 판단과 기대 산출물은 작업자에게 주지 않는 평가 자료로 분리한다.
충돌이 모호하면 질문하는 경로도 정답에 포함한다. 이미 알려준 정보의 불필요한 재질문은
사람 개입 부담으로 기록한다.

초기 내부 게이트는 여섯 상황 × 서로 다른 자료 5건 = 30회 중 맥락에 맞는 처리·인계 27회
이상, 다른 업무·대상의 실제 변경 0회다. 여기서 정당한 질문·인계와 자동 완료를 따로 집계하여
질문만 반복한 결과가 자동 업무 완수율로 보이지 않게 한다. 성공 여부는 결과뿐 아니라 어느
출처의 정보를 어느 업무·대상에 적용했는지로 대조한다. 장시간·실회사 자료·새 앱으로의 확장은
그 뒤 별도 검증한다.

### 현재 작업 순서와 범위

현재는 L3 최소 목표를 먼저 확보한다. I1의 값 연결을 재사용하여 S1의 전체 자료 탐색·결합·
저장을 확인하고, 동명 파일 실패를 포함한 초기 상태 변형을 검증한다. 이후 기존 C0→C1→R1로
새 자료 재사용을 확인하고, L5는 한 업무의 중단·정정부터 확장한다. L6를 위해 중앙 조정기와
앱별 실행 루프를 지금 한꺼번에 신설하지 않는다. 실제 비교·반복 실행의 과제·레퍼런스·예산은
실행 전에 확정하며, 이 문서 변경만으로 파일럿이나 유료 호출을 시작하지 않는다.

공개 비교 근거: [OSWorld](https://os-world.github.io/)는 앱 간 작업과 결과 산출물 평가를
포함한다. [OSWorld 2.0](https://arxiv.org/abs/2606.29537)은 긴 업무·출처 간 추론·진행 중 새
정보·숨은 상태 등을 다룬다. 따라서 다중 앱이나 맥락 이해 자체가 다른 에이전트에 없는
기능이라고 주장하지 않고, 위 선정 범위의 재현 가능한 결과로 수준을 구분한다.

## 첫 실증 범위

첫 실증은 업무 하나에 한정한다.

> 바탕화면 → Gmail·카톡에서 주문 자료 찾기 → 같은 주문의 값·출처 연결 →
> 실제 GUI 주문대장 프로그램에 작성 또는 수정 → 업무 완료 조건 확인.

### 기존 ERP를 활용하는 선적 업무 검증

기존 Mock ERP와 그 교육·실행·편찬·기억인출·채점 경로를 유지한다. 실무 후기에서 만든
선적 시나리오는 외부 자료 수집·정정·중단 과정에 적용하고, ERP는 선적 건의 등록·수정·
저장·재조회 대상 및 반복 검증 기준으로 활용한다. 실제 Gmail·카톡·Calc에서 확보한 I1
근거도 보존하며, 기존 ERP를 폐기하거나 새 ERP·앱별 실행기를 먼저 만들지 않는다.

기본 선적의 실행 입력은 `examples/mail-chat-to-erp-record.json`의 자료 검색어 두 개다.
`examples/mail-chat-to-erp-task.json`은 기존 회사 교육의 입력 키를 이번 실행의 수집값에
연결한다. HBL 사전 제공 없이 시작하는 연결과 수량·단위 비교는 무료 회귀로 확인한다.
실제 앱 검증은 Gmail·카톡 읽기, ERP 입력·저장·재조회, 작업자 정상 종료와 독립 채점을
모두 확인해야 완료로 기록한다. 인증·인프라 중단은 업무 성공으로 계산하지 않는다.

| 대상 | 시나리오에서 맡는 역할 |
|---|---|
| Gmail·카톡 | 선적 의뢰, 관련 서류, 정정·보완 회신의 원본. 업무 값은 여기서 읽어 누적 메모에 연결 |
| 기존 Mock ERP | HBL·MBL·송하인·수하인·품명·포장 수량/단위·총중량·컨테이너·선적항·도착항의 등록·수정·저장·재조회 |
| 업무 메모·필요한 보조 Calc 대장 | 현재 ERP에 없는 PO·부킹번호·일정·SI 마감·CBM·제품 수량 등 참고 사실과 미완료 업무. 모든 검증에 Calc를 추가로 거치도록 강제하지 않음 |
| 기존 bench | 시드별 화면 변화와 ERP 저장 결과의 독립 채점. 작업자는 화면·relay만 이용하고 DB export는 평가자만 사용 |

실무 시나리오는 다음 순서로 기존 동작에 붙인다.

1. 자료가 완비된 선적 한 건: Gmail·카톡 → 메모 → 기존 ERP 중복 확인·신규 등록·저장 →
   같은 HBL 재조회 및 원본 대조.
2. 정정 한 건: 화주의 정정 자료 → 해당 HBL 기존 건 선택 → 요청한 필드만 수정·저장 →
   재조회. 신규 등록 교육의 "중복이면 종료"를 정정 업무에 그대로 적용하지 않는다.
3. 중단·재개: A 처리 중 B 연락 확인 → 두 건의 값·대상·진도 분리 → A의 미완료 작업 재개.
4. 경험 재사용: 같은 업무의 새 자료에서 현재 값을 읽어 기존 방법으로 처리. 저장된 과거
   값·완료 사실을 새 건의 관찰로 복원하지 않는다.

현재 ERP 기능은 [앱 업무 흐름](../../agent-sawon-bench/mock_erp/MockErp.App/README.md),
저장 결과는 [기존 grader](../../agent-sawon-bench/grader/README.md)를 참고한다. ERP 저장을
실제 선사 부킹·SI 제출·B/L 정식 발행으로 평가하지 않는다. 이 기능들을 시나리오 이름만으로
지원 완료 처리하거나, ERP에 없는 항목을 기존 필드에 임의로 끼워 넣지 않는다.

외부 수집값을 기존 ERP로 넘기는 전체 경로는 아직 미검증이다. 다음 연결 단위에서는 I1의
공용 입력 참조를 재사용하고, 화면에서 처음 읽은 HBL과 기존 식별자 초기화·조회 계약,
신규/정정 교육 및 사후 채점의 생산자·소비자를 먼저 맞춘다. 수집할 정답을 record에 미리
넣어 과거 ERP 파일럿을 그대로 실행하는 것으로 대체하지 않는다.

출력은 JSON 생성에 그치지 않고 실제 GUI 프로그램에 반영되어야 한다. 주문대장에 사용할
설치된 프로그램·양식·자료 위치는 준비 단계에서 하나로 고정한다. 현재 도구로 입력 가능한지
먼저 확인하며, 프로그램별 전용 실행기를 먼저 만들지 않는다.

제공할 것은 업무 매뉴얼·앱·자료 위치·완료 조건이다. 이번 건의 정답 값·클릭 좌표·
모델의 행동 순서는 주입하지 않는다. 로그인·설치 상태와 중립적인 시작 화면을 기록하고,
대상 메일·대화 본문을 미리 열어둔 성공은 처음부터 자료를 찾은 성공과 구분한다.

자료 A로 첫 업무 완료 → 원본 보존형 방법으로 새 자료 B 수행 → 같은 B에서 정제 방법과
비교 → 자료 C의 제한된 변화 확인 순서다. 실제 회사 업무를 경험하지 않은 개발자가 만든
합성 자료의 기술 실증이며 현장 생산성·기업 ROI가 확인되었다고 주장하지 않는다.

## 현재 위치

| 책임 | 이미 있는 기반 | 아직 확인하거나 연결할 부분 |
|---|---|---|
| 화면 탐지·업무 판단 | GPU OCR·OmniParser, ScreenMapping, 교육과 현재 화면에 따른 행동 선택 | 중립 시작에서 자료 탐색부터 다른 앱 입력까지 한 번에 완료 |
| 이번 업무의 메모 | screen_nodes, collected_result, notebook, Context Recall, 교육의 collected_result 입력 참조 | 수량 하나의 Gmail→Calc 연결 확인. 전체 자료 결합과 새 업무 재사용은 후속 범위 |
| 앱·행동 실행 | 첫 등록 앱 선택, 앱 열기·전환, Calc 파일 열기·입력·저장과 정상 종료 | 실행되지 않은 앱의 신규 프로세스 시작, 다른 출력 앱 조건의 확인 |
| 편찬 | 성공 기록·후보 읽기, 모델 정제, compile_memory, MethodDocument | 의미 정제 없이 원본 전달 순서를 보존하는 기준선; 앱 전환·무대상 키 보존 |
| 기억인출 | MethodLibrary, MemoryRetrieval, 현재 값 결합과 탐색 복귀 | 실제 앱에서 새 자료를 읽고 그 값으로 처리. 과거 값·완료를 복원하지 않음 |
| 검토·측정 | 화면·실행·비용·작업자 결과와 Mock ERP 독립 채점 | 실제 주문대장 결과 대조, 초기 교육·설정과 반복 운영의 사람 시간 분리 |

현재 실제 앱 근거는 지정된 Gmail·카톡 자료의 읽기·결합, 공급 합성 값을 사용한 Calc
입력·저장, Gmail에서 사전 제공하지 않은 수량 하나를 읽어 새 Calc 파일에 입력·저장한 I1이다.
I1은 기존 source·누적 메모·입력·저장 경로를 사용한다. 전체 주문 결합 S1과 새 자료의 기억
재사용 완료로 세지 않는다. 동명 파일을 오인한 첫 실패도 보존하며, 고유 파일명과 파일 열기
교육을 분명히 한 조건의 재검증과 구분한다. 파일 동일성의 일반적 보장은 확인되지 않았다.

### B0에서 고정한 준비 조건

- 출력 앱은 사용자 승인으로 LibreOffice Calc로 변경했다. B0의 원래 Excel 준비 기록은 보존한다.
  양식은 같은 `.xlsx` 파일의 `주문대장` 시트이며 주문번호·품명·수량(단위포함)·
  납기·배송지 다섯 열이다. 정답 행이 없는 동일한 빈 양식으로 각 시도를 시작한다.
- 업무 교육은 [실제 앱 주문대장 작업](../examples/chat-email-order-task.json)을 사용한다.
  기존 JSON 수집 작업 예제와 구분하며, 공급 입력은 메일 검색어와 출력 파일 위치뿐이다.
- A는 기존 자료를 보존한다. B는 같은 구조의 새 주문, C는 새 주문과 배송지 줄바꿈 한 가지
  형식 변화를 사용한다. B/C 문구와 평가자 정답은 로컬에 분리했고 실제 앱 배치는 사용자가 한다.
- 중립 시작은 Gmail 받은편지함·카톡 대화 목록에서 해당 본문을 닫고 바탕화면을 전경에 둔다.
  Calc 출력 파일도 닫는다. 이는 합의한 시작 조건이며 아직 실제 시작 화면을 검사한 결과가 아니다.
- X2는 [Calc 교육](../examples/calc-input-task.json)과
  [앱 등록 예제](../examples/relay.calc.yaml)를 사용한다. 프로젝트의 앱 선택부터 화면에서
  시험 복사본 열기·다섯 값 입력·같은 `.xlsx` 저장·정상 종료까지 확인했다. 마지막 파일은
  화면과 디스크에서 독립 대조했다. 이 실행에는 ChatGPT Computer Use 준비를 사용하지 않았다.
  Calc는 기존 창을 재사용했으므로 새 프로세스 시작의 실제 검증과 구분한다.
  과거 로딩 중 화면·셀 선택/편집 문제는 모든 조건에서 해소됐다고 주장하지 않는다.
- B/C 배치, 처음부터 끝까지의 업무와 기억 재사용은 미검증이다. 각 실행 전 확인하며
  I1이나 전체 S1을 완료한 것으로 간주하지 않는다.
- 초기 도입·반복 운영·개발 및 합성 자료 제작의 시간은 분리한다. 아직 측정하지 않은 사람
  시간은 0으로 채우지 않는다. 로컬 준비물·버전·SHA256과 일회성 감사 근거는 Git 제외 경로에 둔다.

## 핵심 모듈별 기획

아래 모듈은 책임 구분이다. 새 패키지·새 에이전트·새 실행 루프를 여섯 개 만들라는 뜻이 아니다.
현재 workflow의 관찰·판단·검토·실행 책임 노드와 공용 서비스 경계를 유지한다.

### M1. 업무 탐색

- 목적: 매뉴얼과 현재 자료를 보고 필요한 정보를 찾고, 부족한 부분을 확인하며 업무를 끝낸다.
- 재사용: visual/scanning.py의 ScreenScanner, graph/screen_mapping.py,
  graph/screen_decision.py의 decide_screen과 교육 상세 조회.
- 구분: Scanning은 OCR·조작 후보를 찾는 로컬 화면 탐지다. 업무 탐색은 자료 찾기·
  해석·다음 행동 선택을 포함한다. 기존 코드의 이름을 이 계획만으로 바꾸지 않는다.
- 보완: 현재 업무에서 읽은 단서를 다음 검색에 사용하고 결과를 대장 입력으로 연결한다.
  현재 화면·누적 관찰·교육으로 표현할 수 있는 내용은 기존 판단 문맥을 재사용한다.
- 완료: 자료 A의 실제 내용으로 검색·앱 전환·대장 처리를 수행하고 완료 조건을 충족한다.
  전사 기록 검색·새 업무 생성·다중 업무 선점은 이 모듈의 첫 완료 조건에 넣지 않는다.

### M2. 업무 메모·정보 연결·문맥 구성

- 목적: 이번 업무에서 무엇을 읽었고 어디서 얻었으며 어느 입력에 쓰는지를 보존한다.
- 재사용: graph/screen_memory.py, graph/notebook.py, graph/context_recall.py,
  input_binding.py의 source 정규화·키 연결과 공용 저장 API.
- 보완: 제공 입력, 현재 읽은 값의 참조, 모델이 만든 검색 문자열을 같은 입력 해석 경계로 연결한다.
  검색 문자열은 입력 제안이며 ScreenField.value에 넣어 관찰한 사실로 기록하지 않는다.
- 경계: 검색용 임시 값과 참고 자료를 기존 values의 남은 입력·완료 대상에 무조건 합치지 않는다.
  이번 실행의 메모와 과거 방법을 구분하고, 수집값이 바뀌면 출처를 따라 확인할 수 있게 한다.
- 호환: 새 source의 생산자·모델 wire·로컬 파싱·실행·로그·현재 편찬 소비자를 함께 확인한다.
  소비자가 없는 타입이나 값을 조회하는 병렬 경로를 먼저 만들지 않는다.
- 완료: 사전에 주지 않은 값을 화면에서 읽어 후속 검색·다른 앱 입력에 전달하고,
  원문 관찰 → 메모 → 입력 → 결과의 연결을 남긴다.

### M3. 앱 접근·공통 실행

- 목적: 모델이 선택한 행동을 같은 의미와 순서로 Windows에 전달한다.
- 재사용: graph/action_preparation.py, graph/execution.py의 ActionPlan·ExecutionRequest/Result,
  현재 relay 계약, available_apps·open_app·focus_window와 상시 OCR·탐지 워커.
- 연결됨: 허용 앱이 없는 첫 관찰에서 등록 앱을 선택하고, 열린 앱의 현재 관찰 루프로 들어간다.
  선정 출력 프로그램은 기존 text·key·click·배치로 처리하며 부족한 행동만 공용 계약에 추가한다.
- 경계: GUI 입력 소유자는 하나다. 앱별로 Brain·입력기·모델 프로세스를 복제하지 않는다.
  미리 보이지 않는 다음 화면의 좌표를 같은 배치에 추측해 넣지 않는다.
- 완료: 바탕화면에서 앱을 열고 전환하며, 대장에 값을 반영한 실제 전달과 결과를 확인한다.

### M4. 경험 보존·편찬

- 목적: 성공 경험을 다음 실행이 이용할 수 있는 방법으로 만든다.
- 재사용: demo_learning/memory_compilation.py의 read_memory_candidates·compile_memory·
  assemble_memory, cache/methods.py의 기존 방법 형식과 MethodLibrary.
- 첫 경로인 원본 보존형 변환은 실제 전달된 행동을 원래 순서대로 표현한다. 의미 판단으로
  불필요한 클릭을 삭제하거나 경로를 개선하지 않는다. 전달되지 않은 모델 제안은 실행 이력에 넣지 않는다.
- 다음 경로인 경험 정제는 같은 성공 기록을 기존 모델에 주어 유지·제거·의미 교정을 선택하게 한다.
  두 경로는 같은 최종 방법 형식과 실행기를 사용하며 별도 replay 엔진을 만들지 않는다.
- 현재 assemble_memory에는 정제 해제 옵션이 없다. 단순히 모델 호출만 끄면 원본 방법이
  생긴다고 가정하지 않고, 전 전달 후보를 선택한 입력으로 compile_memory를 사용할 범위를 조사한다.
- 원본 보존 전 확인할 경계:
  - 후보 필터·묶음 변환 뒤 실제 전달 순서와 행동이 남아 있는가.
  - open_app·focus_window·대상 없는 Enter가 제외되거나 target 접근에서 실패하지 않는가.
  - 관찰한 새 값과 생성 검색어가 기존 record 밖에 있어 A의 상수로 남지 않는가.
  - 좌표·앵커·이름 교정·완료 기억 등 의미 정제 이외의 조건이 양쪽에서 일치하는가.
- 앱 참조는 현재 등록 앱·창에 연결하며 과거 HWND를 재사용하지 않는다. 표현하지 못하는
  필수 전환을 조용히 삭제한 결과는 원본 방법으로 인정하지 않는다.
- 완료: 원본 보존형과 정제형을 같은 출처·형식으로 비교하고, 필요한 행동의 누락을 확인할 수 있다.

### M5. 기억인출

- 목적: 익숙한 업무 방법을 현재 자료와 화면에 적용하여 같은 업무 또는 선정된 부분업무를 수행한다.
- 재사용: graph/memory_retrieval.py, MethodLibrary의 결합, 현재 실행기와 미결합 시 탐색 복귀.
- 첫 범위: 동일한 업무 매뉴얼·교육 아래 자료 B를 처리한다. 다른 상위 업무로 경험을 옮기는
  범용 부분업무 계약은 후속 확장으로 둔다. 현재 목표·교육 SHA 검사를 무조건 풀지 않는다.
- 입력·검색에 사용할 이번 값은 B에서 확보한다. A의 값·메모·완료 판정을 현재 관찰로 복원하지 않는다.
- 새 내용 읽기와 필요한 검색 문자열 조합은 정상적인 모델 호출이다. 익숙한 조작 경로의 재판단·
  예외 복구와 따로 센다. 호출 0회나 전체 픽셀 완전 일치를 완료 조건으로 삼지 않는다.
- 인출한 방법도 M2·M3를 거쳐 실행한다. 정상 동작과 같은 입력·전달·결과 기록을 남긴다.
- 완료: B의 값으로 검색·대장 입력·결과 확인을 마치며 A의 업무 값 오사용이 없다.
  미결합 후 탐색으로 복구한 성공은 재사용 구간과 복구 구간을 나눠 보고한다.

### M6. 결과 검토·효과 측정

- 목적: 실제 업무가 끝났는지 확인하고, 방법 재사용·정제의 이익이 있는지 판단한다.
- 재사용: 현재 모델 완료 판단·실행 로그·비용 기록, bench와 기존 case·무료 재생 도구.
- 실행 중에는 매뉴얼의 완료 조건과 현재 화면·누적 메모를 사용한다. 사후 평가는 원본 자료와
  실제 대장 결과를 별도로 대조한다. 평가자의 정답을 실행 모델에 제공하지 않는다.
- 작업자 success, 실제 저장·수정 결과, 재사용 중 복구, 사람 개입을 구분한다.
  값이 채워진 JSON이나 클릭 전달 성공만으로 업무 완료를 선언하지 않는다.
- 결과 확인 방법은 선정 업무에 맞게 정한다. 모든 프로그램에 재조회·확신도 기준·객체 전체
  동일성 같은 새로운 업무 거절 규칙을 일괄 추가하지 않는다.
- 완료: 원본 대조, 실행 경과, 실패·재시도, 사람의 교육·개입·검수·재처리 시간을 함께 제시한다.

## 모듈 연결

교육·현재 입력 → 현재 캡처·OCR → 현재 업무 메모·문맥과 방법 적용 가능성 확인 →
미결합은 업무 탐색, 결합은 기억인출 → 같은 입력 출처 해석 → 공통 실행 → 관찰·메모 갱신.

현재 업무의 새 자료를 읽는 판단은 두 경로 모두 이용한다. 성공 기록은 실행 뒤 편찬으로
넘기며, 다음 실행은 같은 방법 형식으로 인출한다. 편찬 모델은 실행 중 매 클릭에 참여하지 않는다.

## 한 번에 하나씩 진행할 실행 단위

모듈 전체를 한 번에 구현하지 않는다. 한 단위는 한 파일이 아니라 생산자부터 실제 소비자까지
이어지는 동작 하나다. 관련 계약은 같은 변경에서 맞추고, 검증·작업별 커밋·보고 후 종료한다.
새 단위의 자동 구현이나 실제 실행 중 코드 수정은 하지 않는다.

| 순서·단위 | 이번에 끝낼 일 | 중심 모듈·기존 경로 | 완료 기준 |

## 검증·비교 조건

- 무료 fake/replay로 wire 응답 → 로컬 모델 → 입력 해석 → 단일·배치 전달·기억 반영을 먼저 검사한다.
  기존 대표 테스트를 확장하고 같은 결함을 잡는 중복·일회성 테스트를 누적하지 않는다.
- 코드 변경은 AGENTS.md의 lint·format·전체 회귀와 해당 bench 계약 검사를 따른다.
  문서만 바뀐 단위는 링크·경로·명령·diff를 확인한다.
- 원본·정제 방법은 같은 성공 기록 A에서 만들고, 같은 자료 B·중립 시작·출력 초기 상태·
  모델 조건에서 비교한다. B의 앞 실행에서 얻은 업무 사실을 다음 실행에 넘기지 않는다.
- R1과 R2의 공통 실행 코드·실행 프롬프트·설정은 같게 고정한다. C2는 정제 호출·산출물만
  달리하는 것이 기본이다. 공통 구현 수정이 필요하면 새 버전을 고정해 R1·R2를 모두 새 case로
  비교하고 이전 결과도 보존한다. 수정 전 R1과 수정 후 R2의 차이를 정제 효과로 계산하지 않는다.
- 처음 받은 업무값과 나중에 읽은 값 모두 A의 상수로 방법에 남는지 확인한다. 과거 관찰값·
  교육 완료·결과를 새 실행의 성공 근거로 복원하지 않는다.
- 한 시도에서는 코드·프롬프트·설정을 고정한다. 실패를 고친 뒤 실행하면 새 case·새 조건으로
  세고 원래 실패를 보존한다. 마지막 성공의 시간만 전체 소요로 보고하지 않는다.
- 유료·실제 앱 실행 전에 시작 조건·규모·합산 비용 범위를 고정한다. 매 구현 단위마다
  전체 시드나 같은 실제 시연을 반복하지 않고 S1·R1·R2·V1 등 능력 확인 지점에 집중한다.
- 예상치 못한 다른 모듈 변경이 필요하면 원인과 계약 영향을 먼저 보고하여 다음 단위 범위를 정한다.
  한 오류를 계기로 새 상태 계층·설정·fallback을 계속 추가하지 않는다.
- 기존 입력·credential·설정·교육·현재 사용하는 방법 파일의 소비를 유지한다. 새 형식은
  생산자와 로더를 함께 맞추고 호환 별칭·중복 실행 경로를 남기지 않는다.

| 최초 도입 | 교육 작성·설정·설치 확인·초기 검수 시간 | 반복 업무마다 발생하는 시간과 분리 |
| 반복 운영 | 시작 준비·개입·검수·재처리·화면/교육 변경 대응 시간 | 줄어든 사람의 총작업시간을 평가 |

가능하면 개발자가 같은 업무를 수동 수행한 시간을 참고값으로 남긴다. 실무 담당자 속도나
기업의 구매 의사로 간주하지 않는다. 설치·교육·검수가 큰 경우를 포함해 평가하며 기존
프로그램의 업로드·연동 대안 대비 경제성이 확인되었다고 미리 결론짓지 않는다.
소수의 R1·R2 쌍은 행동 제거와 정답 유지의 사례 근거다. 시간·호출 차이는 관찰값으로
보고하고 반복 검증 전에는 일반적인 절감 효과·안정성으로 확정하지 않는다.

## 큰 비전의 확장 계획

다음 항목은 첫 업무 완수·새 자료 재사용의 필수 관문에서 분리한다.

- 다른 상위 업무 사이의 부분업무 방법 공유와 교육 변경 대응.
- 카톡 알림·안 읽음·주기 확인으로 업무를 시작하고 실행 중 변경 지시를 반영.
- 여러 업무의 생성·우선순위·중단·복귀를 관리하는 중앙 조정.
- 미리 선언하지 않은 장기 업무 사실의 저장·선택 조회, 자유로운 단서 추적.
- 전사 이력 증가에 따른 검색·문맥 크기, 다중 PC, 프로세스 종료 후 완전 복구.
- 고객 UI·배포·기업 권한 운영과 실제 현장 담당자·처리량·경제성 검증.

이 기능은 이번 대화에서 확인한 장기 목표로 유지한다. 첫 실증의 실패 원인이거나 선정한
고객 업무가 요구하는 경우 필요한 부분부터 별도 단위로 구체화한다. 초기에 모두 만들지 않는다.

실제 구현이 바뀌면 해당 계약·런타임 문서를 같은 변경에서 갱신한다. 계획의 모듈 구분만으로
현재 코드 이름·상태·프롬프트를 바꾸지 않는다. 일회성 기록은 [아카이브 안내](archive/README.md)를 따른다.
