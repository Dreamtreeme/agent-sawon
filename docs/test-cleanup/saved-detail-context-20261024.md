# 저장 상세 반복: 재생·수정과 원인 계층

2026-10-24. 대상은 093 시드 3의 저장 이후 반복이다. 사용자가 직접 창을 이동한 로그인
구간은 제외한다. 원본 화면·요청·응답은 비공개 case에 보존하며 이 문서에 복제하지 않는다.

## 확인한 인과관계

093 seq 534의 결과 행 열기는 성공했다. 상세 프레임 `1b591a82`의 제목은 수정 화면이고
저장 번호 1과 입력값이 보인다. seq 549–550에서 모델은 닫기 계획을 만들었고, seq 552–554에서
코드가 재조회 단계 완료·상세 검토 시작·4개 필드 확인을 기록했다. seq 559는 동일 obs_id라는
이유로 앞서 만든 계획을 재사용했고 seq 564–566은 닫기를 전달했다.

두 번째 상세 프레임 `937da561`의 원문 요청은 post_save_detail_review=true와
saved_result_open_pending=true, 완료 목록의 requery-saved-record와 같은 focused_step_id를
동시에 포함한다. 모델은 seq 602에서 다시 닫기를 선택했다. 첫 반복과 달리 이 요청에는
상세 검토 시작 정보가 이미 있으므로 '상태 갱신 지연 하나만 고치면 모두 해결된다'는 해석은
지지되지 않는다. 모델은 기존 pending 처리 지시도 받았으나 따르지 않았다.

품명 라벨 아래 입력칸은 이 프레임에서 viewport 밖에 잘려 있다. 이를 빈 입력값 또는 DB와
상세 화면의 값 불일치로 확정할 수 없다. 후속 스크롤 뒤 값이 나타난다. seq 711의
action=click, keys=pagedown 응답은 서로 맞지 않는 실행 필드로 거절됐으며 이번 수정 대상이 아니다.

## 추상화 수준별 근원

| 수준 | 문제 | 코드·실행 근거 |
|---|---|---|
| 화면 행동 | 열었던 상세를 닫고 다시 연다 | 093 seq 534 → 549 → 564, 587 → 602 → 615 |
| 함수 순서 | scan 내부에서 다음 계획까지 만든 뒤 상세 검토 상태를 확정한다 | engine._observe → ScreenScanner._resolve → _detect_visual → _begin_saved_detail_review |
| 계획의 유효 범위 | obs_id가 같으면 업무 문맥이 바뀌어도 계획을 재사용한다 | _selection_call의 proposal_reused; seq 552 뒤 seq 559 |
| 상태 수명 | 장기 검토 시작 여부가 단기 전환 pending 해소까지 막는다 | _begin_saved_detail_review의 기존 not model_saved_detail_review 조건 |
| 상태 소유권 | 모델의 선택이 관찰로 완료된 교육의 초점을 되돌린다 | _advance_taught_procedure의 무조건 active_taught_step 대입 |
| 설계·검증 | 해석과 다음 계획을 한 응답으로 최적화하면서, 응답 처리 도중 변경되는 문맥의 유효성 계약이 빠졌다 | 기존 테스트는 최종 메모·증거 기록 순서만 검사하고 stale 계획의 실제 전달까지 검사하지 않음 |

검토 중=true와 열기 대기=true는 재진입 도중에는 양립할 수 있다. 잘못은 두 값의 공존 자체가
아니라 도착한 뒤에도 대기가 소비되지 않는 것이다. 독립 bool을 금지하거나 FSM을 새로 만드는
것보다 기존 함수가 상태의 수명을 정확히 책임지는 것이 이번 결함에 맞는 수정이다.

가장 상위에서 확인된 문제는 '현재 사실과 계획이 같은 시점의 문맥을 가리키는가'라는 계약이다.
노드 이름이 Observation/Decision으로 나뉘어 있어도 실제 실행 순서가 그 계약을 보장하지 않는다.
이는 모든 모델 오판의 원인이라는 주장이 아니다. seq 451의 중복 저장은 이미 save_issued와
적절한 교육을 받은 모델의 선택이었고, 이번 변경으로 사라질지는 별도 실측이 필요하다.

## 변경

제품 커밋: `c48fedd`.

- `engine.py`: 첫 상세 검토 확정 후 현재 증거를 기록하고, 확정 전 생성한 다음 계획·후보·계획
  오류만 해제한다. Decision이 동일 캡처·해석에서 갱신된 문맥으로 재선택한다.
- 재진입에서는 pending 전환을 먼저 소비하고, 이미 시작한 검토의 확인값은 유지한다.
- 완료된 교육 단계의 선택은 교육 초점을 되돌리지 않는다. 행동을 거절하지 않으며 미완료
  과거 단계는 재선택할 수 있다.
- `context.py`: pending_actions에 출발 screen_kind, 물리 action, 의도한 subgoal을 보존한다.
  의도는 성공 증거가 아니며 과거 ref·좌표는 현재 대상으로 노출하지 않는다.
- 새 클래스·정책 계층·모델 응답 필드·버튼명 차단을 추가하지 않았다. 실행 제약 완화도 없다.

이 수정은 첫 상세 진입에 재판단 호출을 추가할 수 있다. 일반 관찰마다 호출을 추가하지 않는다.
새 메서드 선택도 같은 공용 경로를 사용한다. 광범위한 '어떤 상태가 바뀌면 모든 계획 폐기'
정책으로 확장하지 않았다.

## 무료 검증

`tests/test_post_save_context.py`의 합성 4건은 수정 전 모두 결함 지점에서 실패했다.

1. 닫기 계획이 생성된 뒤 상세 검토가 확정되는 재생: 수정 전 navigate가 선택됨. 수정 후
   갱신된 문맥으로 선택한 select_tab 좌표만 fake relay에 전달됨. OCR·탐지 각각 1회 유지.
2. 검토 중 상세 재진입: 수정 전 pending이 남음. 수정 후 pending 해소·확인값 보존.
3. 완료 단계 재선택: 수정 전 교육 초점 회귀. 수정 후 현재 초점 유지·미완료 단계 재선택 가능.
4. pending 문맥: 수정 전 출발 화면·물리 행동·목적이 누락. 수정 후 전달됨.

fake의 두 번째 응답은 모델 품질을 증명하지 않는다. 실제 함수의 상태 전달, 계획 교체와 행동
전달을 검증한다. 기존 일반 관찰 1호출 테스트와 상태 경로 동등성 테스트도 전체 검사에 포함된다.

기존 단언 변경: test_worker_context의 pending_actions 전체 딕셔너리 2건에 추가 정보를 반영.
test_detail_observation_commits_review_before_current_evidence의 rejected-plan은 더 이상 폐기된
계획의 오류를 다음 판단에 다시 던지지 않는지 확인한다. 현재 증거 보존 단언은 유지한다.

- 코어 전체: 710 passed (41.16초, 실제 전달 단언 보강 전 전체 검사).
- 전달 단언 보강 후 해당 합성 테스트: 4 passed.

누적 증거가 사라지거나, 일반 화면에서도 재판단이 늘거나, 새 문맥 전의 계획이 실제 전달되면
구현 결함이다. 화면 유사도 강화·모델 교체·완료 기준 완화로 해결됐다고 주장하지 않는다.
