2026-11-02. 기준 core `593e7cb`, 제품 동작은 `4629622`와 같다. 대상은 143에서 남은
(1) 스크롤/분할 배치의 진도 연결과 (2) 실제 경로와 편찬 경로의 차이다.
제품 파일·테스트 파일·프롬프트·설정·실행 원본은 변경하지 않았다. 함수 사본을 현재
프로세스에서만 교체하고 실제 기록 재생 및 명시적인 합성 반례를 실행했다. API·ERP 호출은 없다.

진도 연결 함수가 기억을 고르는 함수와 공유하는 핵심 제약은 **그룹 하나를 통째로 완료한
단위로 취급한다**는 점이다. `replaced_edge`는 원본 그룹 ID 하나이고 행동별 완료 범위가 없다.
실제 다른 행동을 거쳐 같은 결과에 도달한 경우는 `resumed_group_ids`에 별도로 기록한다.
`used`의 전달 소비와 업무 완료는 같은 뜻이 아니다.

## 프롬프트·교육 대조

### 스크롤은 실제 프롬프트와 코드 조건이 충돌한다

`brain/graph/screen_mapping.py:391–394`:

> If inputs are offscreen, use action=scroll with direction=down or up,
> choosing a point inside the current image's scrollable region. The wheel point
> does not need to be inside the named field's bbox; the target names the current context.

모델에게는 이름 붙인 필드의 bbox 밖에서도 스크롤할 수 있다고 안내한다. 실행 경로도
스크롤을 전달했다. 그런데 기억 진도 연결은 같은 휠 동작에 입력칸 bbox 조건을 적용했다.
143 same seq122의 다섯 입력은 전부 일치하고 마지막 scroll down만 이 조건에서 탈락했다.
원본 `[600,400]`과 실제 `[1137,400]` 모두 화면의 스크롤 영역에 있지만, 원본 target인
품명 bbox는 `[48,604,1059,33]`이다. 원본 point 자체도 해당 bbox 밖이며, bbox 밖의 point는
원본 point와 동일할 때만 통과한다. 제거 대상은 이 **스크롤 귀속 위치 조건**으로 좁힐 수 있다.

### 메뉴 경유를 강제하는 실행 프롬프트는 확인되지 않았다

같은 프롬프트의 `Preserve the taught route and completion conditions.`는 교육 경로를
따르라는 문구다. 회사 001 교육은 조회 결과가 0건이면 신규 버튼으로 등록하라고 한다.
메뉴 복귀는 필수 교육이 아니라 과거 실행에서 나온 편찬 경로다.

실제 same seq92는 기억의 닫기→메뉴 등록 안내를 받고도 신규 버튼으로 직접 들어갔다.
seq122에서 현재 등록 화면을 확인한 뒤 seq128에 옛 경유 그룹 두 개를 소진했다.
따라서 이 문구를 삭제해야 직행이 가능하다는 설명은 실제 기록과 맞지 않는다.

`brain/demo_learning/memory_compilation.py:141–143`의 다음 규칙도 구분해야 한다.

> Never invent, edit, duplicate, merge, or change actions, input sources, coordinates, or markers.
> Return retained candidate IDs in execution order.

이는 편찬 시 실제 전달 기록을 선택하는 규칙이다. 현재 실행의 모델에게 동일 배치를
강제하는 규칙은 아니다. 행동 선택은 candidate ID 단위이고 코드는 원본 행동을 복사하므로
이 문구만 지워도 분할 배치 연결은 해결되지 않는다.

스크롤에만 위치 비교를 제외하면 방향·행동 종류·입력 출처·viewport 조건은 유지된다.
합성 반례의 반대 방향 scroll과 다른 칸 fill은 여전히 연결하지 않았다.
다중 스크롤 영역 간 오연결이나 새로운 전체 ERP 경로는 이번 시험 범위가 아니다.

### 부분 배치와 다른 컨트롤 반례

- 길이 조건만 제거: 실제 changed 5fill에서 `zip(..., strict=True)`가 `ValueError`를 냈다.
- 길이 조건과 strict를 함께 제거: 합성 응답으로 원본의 5fill + scroll 중 **첫 2fill만**
  전달·확인했다. 실제 `remember → delivered → verify_delivery(success=True)`를 통과하자
  나머지 3fill과 scroll을 하지 않았는데 원본 그룹 전체가 소진됐다.
- 효과 검토의 성공은 실제 전달한 배치에 대한 성공이다. 이 검토가 자동으로 생략된 원본
  행동까지 확인하지 않는다. success=False/None에서는 대체 연결을 확정하지 않으므로
  실패 응답도 무조건 완료된다고 설명해서는 안 된다.
- 모든 point/bbox 비교 제거: 같은 source의 다른 위치 fill과, 다른 버튼의 click이 원본과
  연결됐다. 일반 click은 action/source/keys가 `click/None/None`으로 같을 수 있다.
  기존 의미 이름·role·intent 비교는 이 함수에 없으므로 그 자리를 대신해 주지 않는다.

### 첫 그룹 제한 제거

task·active method·pHash·최소 거리 동률 처리는 유지하고 모든 남은 그룹을 비교했다.

- 실제 143 same/changed 닫기 후에는 결과 열기 그룹을 거리 0으로 선택했다.
- 그러나 같은 실제 실행의 첫 메뉴에서는 최초 조회·신규 등록·재조회가 모두 거리 0이다.
  현재 정상 선택하던 최초 조회도 동률로 `None`이 됐다.
- 결과 열기와 상세 스크롤을 직접 전달해도 건너뛴 메뉴·조회 그룹은 소비되지 않았다.
  현재 모델의 단계 완료를 별도 주입하지 않는 재생에서는 최종 completion으로 넘어가지 못했다.
- 합성 입력 전 화면에서는 미완료 입력보다 유사한 뒤쪽 save를 선택했다. 다른 테스트에서는
  선행 복구의 효과가 없는데도 후속 그룹을 선택하거나, 같은 화면의 순차 입력이 경쟁했다.

유사한 화면을 찾는 조건 삭제와, 이미 도달한 업무 결과로 과거 경유 단계를 소진하는 것은
별개다. 첫 그룹 제한만 없애서는 진도 정합성 문제가 해결되지 않는다.

## 정리

1. 스크롤의 point/bbox 귀속 비교는 실제 계약과 충돌하는 삭제 후보다. 무료 기록 재생과
   관련 회귀에서는 문제가 없었다. 클릭·입력의 위치 비교까지 함께 없앨 근거는 없다.
2. 배치 전체 길이 일치는 과도하지만, 현재 `replaced_edge`가 그룹 전체만 표현해서 단순
   삭제하면 잘못된 완료가 된다. 기존 전달 이력으로 여러 배치가 원본의 어디까지 수행했는지
   누적해 연결하거나, 현재 모델의 완료 관찰로 재개하는 책임을 먼저 맞춰야 한다.
3. 첫 그룹만 비교하는 제한도 과도한 상황이 있지만 유사도만으로 모든 후속 행동을 경쟁시키는
   방식은 실제 초기 메뉴와 기존 반례에서 퇴행했다. 현재 도달 상태를 확인한 모델 결과와
   `resumed_group_ids`를 연결하는 기존 경로를 활용할 여지가 있으며, 중간 경유만 완료된
   상황을 어떻게 표현할지는 추가 구현 범위다. 새 상태 기계가 필수라는 근거는 없다.
4. 이번 두 문제를 해결하기 위해 삭제해야 한다고 확인된 프롬프트 문구는 없다. 우선 고칠
   경계는 모델이 허용받은 행동과 코드가 기억 진도에 인정하는 행동의 차이다.
