2026-11-01. 제품 코드 변경 없이 시드 1에서 같은 입력과 6개 값을 바꾼 입력을 각각
1회 실행했다. 두 실행 모두 ERP 10/10, 작업자 exit 0이다. 과거 값을 현재 관찰로
되살리던 결함은 재현되지 않았다. 그러나 행동 이름과 실제 좌표의 불일치, 경로 복귀
실패에 따른 재판단, 응답 변환 실패에 따른 정상 관찰 폐기는 실제로 남았다.

## 후속 재분류: 사람이 업무를 수행한다면 필요한 행동인가

사용자가 요청한 기준에 따라 호출 증가·기술 복구와 사람이 굳이 하지 않을 업무 행동을
분리했다. 같은 기록·작업지시서·ERP 창 동작 코드를 읽어 재검토했으며 추가 모델 호출이나
ERP 실행은 하지 않았다. 아래의 세 기술 경계를 모두 불필요한 업무 행동 또는 즉시
수정할 결함으로 읽어서는 안 된다.

### 실제 실행된 불필요 우회: 처음 조회창을 닫음

사람은 중복 조회 0건을 확인한 화면에 신규 등록 버튼이 있으면 그 버튼으로 등록한다.
이 ERP의 `NavigationForms.cs:109-114`는 이 경로에서 조회창과 검색어를 유지하고,
등록창이 닫힐 때 `Search()`로 결과를 다시 조회한다. 실제 changed 실행도 이렇게 진행했다.

same은 처음 조회창을 닫고 메뉴에서 등록했다. 이 경로도 업무 완료는 가능하지만,
그 선택을 요구하는 업무 조건이나 화면 장애는 발견되지 않았다.

| 구간 | same 우회 | changed 직접 경로 | 추가 행동 |
|---|---|---|---:|
| 신규 등록 진입 | 조회 닫기 → 메뉴 등록 | 조회창의 새 건 등록 | 1 |
| 저장 후 상세 진입 | 등록 닫기 → 메뉴 조회 → 번호 입력 → 조회 → 결과행 열기 | 등록 닫기 → 자동 갱신된 결과행 열기 | 3 |

총 4개 행동 차이(전체 30 대 26)는 이 경로 차이로 설명된다. 저장 후 메뉴에서의 조회와
번호 입력은 이미 조회창을 닫아 버린 상황에서는 필요한 행동이다. 이들 각각을 불필요한
반복이라고 부르면 원인과 후속 복구를 혼동한다. 시간 차이 전체를 4개 행동의 효과로
계산하지는 않는다. 입력값·모델 응답·탐지 대기시간도 달랐다.

### 불필요한 반복 제안: 이미 연 상세를 닫고 다시 조회하려 함

same seq440 직전에는 저장한 번호의 조회 결과행을 더블클릭했고, 현재 화면에 수정창 제목,
같은 번호와 저장 번호가 있었다. 사람이면 그 상세에서 값을 확인하고 아래로 스크롤한다.
교육의 목표도 조회 목록 유지가 아니라 저장한 번호의 상세 입력 화면 진입이다.

응답이 든 이유인 ‘편집 화면이며 조회 화면이 아니다’는 이 목표와 맞지 않는다. 다른 번호나
저장 실패 같은 새로운 모순도 제시하지 않았다. 따라서 닫고 재조회할 업무상 필요는
확인되지 않았다. 다만 이 제안은 미선언 target으로 거절되어 실제 반복 행동은 0회다.
남아 있는 닫기→메뉴 메서드 안내와 현재 상세 진입 사실의 충돌은 설명 후보이며, 모델 단독
오류나 코드 단독 오류로 원인을 확정하지 않는다.

### 이번 불필요 행동 목록에서 제외하는 것

- 상단으로 돌아가 값 확인: 당시 상단 4값은 입력 전달만 있고 관찰 확인이 없었다.
  사람은 입력 중 확인하지만 현재 배치는 입력 후 스크롤까지 끝낸 뒤 관찰한다.
  이 기술적 관찰 시점 제약으로 생긴 왕복이며, 이미 확인한 값을 까먹고 다시 본 것은 아니다.
- 저장 후 상세 상·하단 확인: 교육이 모든 저장값 대조를 요구하므로 필요한 업무다.
- pHash/선두 그룹 조건 때문에 메뉴·조회에서 모델 재판단: 재사용 제약에 따른 계산 비용이다.
  해당 메뉴·조회 행동 자체를 생략해야 한다는 증거가 아니다.
- KeyError 뒤 재호출: 응답 계약 오류 복구다. 13.292초 전부를 불필요한 업무 시간으로 세지 않는다.
- 읽힌 5값의 미채택: 원문은 보존돼 있고, 응답은 상세 진입을 부정하며 화면 소속도 불확실했다.
  문자열이 맞다는 이유만으로 저장 상세 완료 증거로 자동 채택할 수 없다. 미채택 자체를
  결함으로 확정하거나 검증을 없애자고 결론내리지 않는다.

사람 기준으로 남는 핵심은 성공 기록 속의 불필요 우회를 그대로 배운 것과 이미 도달한
상세를 아직 가야 할 화면처럼 취급한 반복 제안이다. 이후의 기술 분석과 호출 수는

## 실제로 남은 차이 1: 이름은 신규 등록, 실제 클릭은 닫기

same seq92 응답은 `새 건 등록`의 bbox를 `[352,708,102,41]`, 클릭을 `[403,728]`로
반환했다. 실제 `cf88250e-d882-4dba-946f-815636e52045/capture.png`에서 이 위치는 **닫기**다.
실제 신규 등록은 그 왼쪽 버튼이다. seq111은 그대로 닫기를 전달했고 화면은 메인 메뉴로
바뀌었다. 이후 원본 메서드의 메뉴→등록 경로가 이어져 최종 업무는 성공했다.

요청에 정확한 OCR `새건등록` bbox `[218,714,102,29]`와 `닫기` bbox `[378,713,50,32]`가
모두 있었다. 반면 인출된 `memory_fields`는 닫기 영역을 `새 건 등록`이라고 제공했다.
따라서 OCR 정보 부족이라고 볼 수 없다. 이번 모델은 충돌하는 기억의 이름·좌표를 택했고,
설명은 신규 화면 직행이라고 작성했다. changed seq92는 `[271,728]`의 실제 신규 등록을
선택해 곧바로 등록창으로 갔다.

오라벨의 출처도 실제 기록으로 추적했다. 138-cold의 `case-8936a488e0f34c3faa95c23544cd34ea`
seq112에서 이미 같은 잘못된 이름·bbox가 생성됐다. seq145 모델은 신규 등록을 눌렀지만
메인 메뉴가 나왔으며 신규 입력창은 아직 아니라고 기록했다. 그런데 seq150의 화면 변화
성공과 함께 실행 경로는 남았다. 편찬 그룹 `4b43c1091ded7f85`는 목적을 **조회창을 나가
메뉴로 복귀**로 정리하면서 `observed_fields[name="새 건 등록"]`의 오라벨은 정정하지 않았다.
139의 두 seq92 요청에서 이 구조 기억, 인출 절차, 위 두 OCR 영역은 동일했다.

따라서 이번에 새로 생긴 모델 오독만으로 설명할 수 없다. **실제 다른 화면으로 갔다는
피드백이 있었는데도 구조 기억의 잘못된 의미가 편찬 뒤 남았고 재사용됐다.** 두 호출이
충돌을 다르게 해소한 것은 확인되지만, 변경값이 올바른 해석을 일으켰다고 단정하지 않는다.

seq127은 이 행동을 원본의 실제 닫기 그룹 `4b43c1091ded7f85`와 연결했다. seq128은
`method_effect.success=true`, seq129는 `observed_effect=changed`다. 이 성공 표시는
화면 변경/원본 행동 연결을 뜻하며 모델이 말한 **신규 화면 도착**을 증명하지 않는다.
관련 경계는 `engine.py:_verify_navigation`, `method_effect_verified`다.

## 실제로 남은 차이 2: 현재값 확인 뒤 편찬 경로에 재결합하지 못함

원본 그룹은 상단 5개 입력 직후 하단으로 스크롤한다. 새 현재값 검토는 화면 밖 상단
4개를 확인할 수 없어 하단 입력 후 상단으로 돌아온다. 이 보완 자체는 미확인 값 확인이다.
문제는 그 뒤의 재결합이다.

1. 상단에서 저장·닫기를 실행해 원본 하단 화면과 pHash 거리 14가 발생했다.
2. `_replacement_group`은 원본과의 화면 유사도도 요구해 해당 행동을 연결하지 못했다.
3. 다음 메뉴와 조회 화면은 각각 원본 다음 그룹과 거리 0인데도, `_matching_route`는
   미통과한 앞쪽 닫기 그룹만 검사해 인출하지 못했다.
4. same seq355·381의 2호출, 합계 13.195초는 익숙한 메뉴·조회 행동을 다시 선택했다.
   모델이 재조회 단계를 완료했다고 반환한 뒤 남은 4그룹을 resume했다.

관련 코드: `memory_retrieval.py:_remaining_groups`(192), `_matching_route`(213),
`_replacement_group`(593), `cache/methods.py:screen_similarity_distance`(740).
이 pHash는 **편찬 경로 화면 결합**용이다. ORB의 직전 행동 전후 변화 판정

## 실제로 남은 차이 3: 화면은 열렸지만 관찰 실패로 기록

same seq440은 재조회 결과행 더블클릭 뒤 열린 저장 상세 상단 5개 값을 정확히 읽었다.
그러나 아직 재조회 상세가 아니라고 판단해 닫기를 제안했다. 요청에는 직전 double_click,
`saved_result_open_pending=true`, `saved_detail_candidate`, `window_changed`, 실제 제목
`House B/L 수정`이 모두 있었다. 필요한 진입 문맥이 없어서 생긴 오류로 단정할 수 없다.

응답은 `fields`에 닫기를 선언하지 않았다. `screen_mapping.py:151 field_name`의
`KeyError('닫기')`로 행동과 정확히 읽은 5값이 함께 미반영됐다. seq446~447의
`method_effect=observation_unavailable`, `observed_effect=unchecked`는 실제 창 이동
실패가 아니라 **응답 변환 실패**다. seq455가 같은 화면을 다시 읽어 정상 진행했다.

첫 호출은 4.242초, 재시도는 9.050초였다. 합계 13.292초가 이 두 호출에 들었지만,
정상 상세 검토 자체도 필요한 만큼 전부 절감 가능 시간으로 세지는 않는다. changed에는
이 거절과 같은 화면 재시도가 없었다.

same에서는 저장 상세 상단 5값이 등록 노드에, 하단 6값이 수정 노드에 들어갔다.
이는 실제 상태 분할 관찰이다. 이번 실행의 검증 누락이나 업무 실패는 확인되지 않았으므로
별도의 장애로 확정하지 않는다. changed는 수정 노드 한 곳에 saved_detail 11값을 누적했다.

## 집계가 가리는 범위

  pending에서 뺀다. 아직 결합하지 못한 원본 그룹은 이 분모에 없다.

## 검증 범위와 반증 조건

- source/value 분리 수정은 두 실행의 해당 결함을 해결했다. 순수 인출이 value/현재관찰을
  다시 발행하거나 새 record 대신 옛 값을 입력한 사례가 나오면 이 결론은 반증된다.
- 새로운 시드나 반복 성공률을 측정한 것은 아니다. 동일 시드 두 입력으로 전체 호환성을
  주장하지 않는다. 새 편찬 결과의 개선 효과도 이 실험으로 판단하지 않는다.
- 138은 현재값 대신 과거값을 확인으로 사용했고 계측도 다르므로 54초를 올바른 검증을
  수행한 동등 성능 기준으로 삼지 않는다. profiler 시간은 중첩 inclusive이며 동기 기록
  비용도 포함돼 함수별 합계를 더하면 중복이다.
- 본 작업에서는 제품 코드·설정·프롬프트를 고치지 않았다. 추가 수정 전 실제로 확인한
