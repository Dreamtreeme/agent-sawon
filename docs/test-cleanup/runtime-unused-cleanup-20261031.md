# 정상 기억 인출의 중복 처리와 무효 전달 정리

137 화면·로그·소비자 코드 조사 후 승인받은 순서대로 중복 통합, 무효 전달 삭제,
모델용 문맥 생성 지연을 진행한다. 기존 입력 메모, 실행 검증 조건, 모델 프롬프트는 유지한다.

## 1. 중복 통합

- 이미 준비한 계획을 재사용한다. 대상 보완이나 빈 행동 복구가 응답을 바꾼 경우에는
  다시 준비·검증한다. 응답 비교는 중복 계산 생략 조건이며 행동 거절 조건이 아니다.
- 변경되지 않은 응답은 대상 정리도 한 번 수행한다. 복구로 새 대상을 받은 경우에는
  기존 정리 경로를 거친다.
- 하나의 화면 판단 요청에서 저장 증거 snapshot을 한 번 생성해 실행 계약과 문맥에 공유한다.
- 합성 정상 모델·메서드 입력은 준비/대상 정리 각각 2회에서 1회로 감소한다. 오류 응답을
  모델이 고친 경우와 빈 행동 복구에는 필요한 재검증을 유지한다. 새로 연결한 비활성
  대상의 거절도 유지한다. 기존 테스트의 행동·값 검증에 횟수 단언을 함께 둔다.

수정 전 전체 기준선은 742 passed, 기존 3 xfailed / 59.62초다. 시간은 로컬 환경의
측정값이며 코드 변경의 효과로 단정하지 않는다.

1단계 검증: 전체 746 passed, 기존 3 xfailed / 65.69초, Ruff check/format 및
diff check 통과. 이전 함수를 메모리에 복원하면 중복 검출 3건이 실패하고, 변경 응답의
검증을 무력화하면 비활성 대상 테스트가 실패했다. 실제 모델·ERP 호출은 아직 하지 않았다.

## 2. 무효 전달 삭제

- worker가 소비하지 않는 `ocr_boxes`의 생성·인자·JSON 전달을 제거했다. OCR 실행과
  marker 병합은 유지한다.
- 항상 None인 `SemanticRequest.interpretation`과 engine 전달, 읽는 곳이 없는
  `pending["response"]`, 항상 False인 `allow_literal_anchor` 인자·분기, 함수 입구에서
  이미 확인한 pHash None 조건을 삭제했다.
- 제품에서 호출하지 않는 `MethodLibrary.bind()` 래퍼를 삭제하고 테스트 13개 호출을
  실제 제품 진입점인 `bind_with_context()`로 옮겼다. 같은 response의 행동·입력 키·좌표·
  증거를 계속 확인한다. 무효 전달만 고정하던 단언 2개를 제거했고 테스트 함수는 삭제하지 않았다.
- `needs_image`와 과거 산출물의 앵커 결합 경로는 이번에 변경하지 않았다.

2단계 검증: 전체 746 passed, 기존 3 xfailed / 49.10초, Ruff check/format 및
diff check 통과. 제품 코드 30줄 순감소. 삭제한 이름의 제품·테스트 잔여 참조는 없다.

## 3. 모델 문맥 생성 지연

- 기존 `DecisionPromptContext`를 한 요청 안에서 지연 생성한다. 실행 capability는 즉시
  준비하고, 메서드가 결합되지 않거나 복구·캐시 조회가 필요할 때 notebook·화면 트리·교육
  문맥을 조립한다. 정상 메서드 경로에서는 크기 측정용 JSON 직렬화도 하지 않는다.
- 화면 투영과 메서드 문맥은 이전과 같은 결합 전 시점에 확보한다. `match_pattern`이
  화면 대상·purpose·bindings·선택 메서드를 바꾸므로 이 두 원천까지 늦추면 복구 프롬프트와
  캐시 키가 달라진다. 이 비용까지 없앴다고 주장하지 않는다.
- 합성 복구 테스트에서 결합 중 위 값이 바뀌어도 정렬하지 않은 전체 JSON, 실제 프롬프트
  문자열과 캐시 키가 이전 시점의 문맥과 같다. 두 snapshot 중 하나를 늦추는 결함을
  메모리에 주입하면 각 비교가 실패한다. 정상 메서드는 회상 조립 0회, 모델·재계획·빈 행동
  보완은 1회다. 프롬프트 문구와 모델 응답 계약은 변경하지 않았다.
- 전체 검사에서 옛 `recall_context(request)` 추적 래퍼와 선행 회상 순서를 가정한 2건이
  실패했다. 래퍼가 새 선택 인자를 전달하도록 바꾸고 실제 패턴 확인 후 회상 순서로 갱신했다.
  입력 출처·메모 보존·최종 실행 행동 단언은 유지한다.

정리 전 `882c689` 대비 제품 Python 전체는 6줄 순감소다. 삭제량만으로 효과를 주장하지 않고,
중복 호출과 문맥 생성 횟수, 실제 화면 결과를 따로 확인한다. 테스트·설명 추가분은 이 수치에
포함하지 않는다.

3단계 최종 검증: 전체 747 passed, 기존 3 xfailed / 50.27초. Ruff check/format,
Vulture(min-confidence 80, 경고 0), diff check 통과. 정상/보완/복구와 실제 화면의 동작
동등성은 별도로 확인하며 기존 예상 실패 3건은 이번 정리로 해결했다고 주장하지 않는다.

### 기존 산출물의 동작 보존

137과 138-fixed에서 같은 12개 그룹을 같은 순서로 전달했다. 실제 요청 26개의 행동 종류,
좌표, 입력값, 키, reason이 같았다. 비교에서 제외한 것은 실행별 action/observation/capture
ID와 증거 참조다. 최종 화면 노드 메모도 observation_id를 제외하면 같고, 최종 확인 필드와
저장 후 확인 필드는 각각 11개였다. 완료 기억 결합은 양쪽 모두 1회다.

읽기 전용 `sys.setprofile` 계측으로 138-fixed의 계획 준비·대상 정리·미사용 컨트롤 정리는
각 13회, `recall_context`와 `assemble_state`는 0회였다. 기존 코드에서 매 판단마다 만들던
`match_context_size` 기록도 13회에서 0회로 줄었다. 기존 137은 함수 프로파일을 수집하지
않았으므로 과거 실제 함수 횟수를 측정값처럼 표기하지 않는다. 정상 준비 2→1회는 코드와
합성 회귀 테스트로 확인했고, 실제 중복 guard 기록은 2→1회로 줄었다.

전체 시간은 오히려 11.690초 늘었다. 그중 시작 plan부터 첫 screen_similarity 기록까지가
3.828→14.040초로 10.212초 늘었고, 첫 메서드 결합부터 종료까지는 17.363→18.859초였다.
행동 전달 지연 합계는 11.252→11.434초였다. 첫 구간의 세부 원인은 기록만으로 확정하지
못했다. 두 실행의 환경 초기화와 계측 조건도 같다고 보장할 수 없어 속도 향상을 주장하지 않는다.

### 새 탐색·편찬·인출에서 확인한 차이

새 탐색은 원격 21회(판단 10, 빈 행동 보완 2, 교육 조회 1, 입력 검토 1, 완료 검토 7),
로컬 탐지 13회였다. 이전 137 탐색의 원격 14회·125.995초보다 늘었다. 이번에는 조회와
등록 사이, 저장 후 재조회 전에 메인 메뉴를 거치는 다른 경로를 선택했다. seq 215의 모델
응답은 key 행동에 빈 keys를 반환해 기존 Literal 검증에서 거절됐고, 후속 판단으로 복구했다.
정리 코드가 새 거절 조건을 추가한 것은 아니다. 실행을 고쳐 재시도하지 않았다.

편찬은 후보 16개 중 c007/c008(하단 입력 후 상단을 보고 다시 하단으로 돌아오는 스크롤)을
제거해 14개 그룹을 만들었다. 산출물 SHA-256은
`1b76842dbf3885b25cc7a2652cb3922b2289f556bf72a8bcce820a9ffa7fa2ea`다.

새 인출은 reuse 12그룹과 adaptation 2그룹을 전달했다. 원격 호출 두 번은 모두
completion_review이며 seq 354는 재조회 결과 행 열기, seq 380은 상세 상단 값 확인 후
하단으로 스크롤하기였다. 첫 호출 앞 seq 348과 두 번째 호출 앞 seq 374에서 화면 유사도
선택이 matched=false여서 탐색으로 전환했다. 메서드 실행 중단이나 화면 캐시 선택은 없었다.
따라서 전체 업무 성공과
모델 없이 재현한 성공은 구분한다. 이번 새 산출물의 완전 재현은 성공하지 않았다.

새 인출의 계획 준비·대상 정리·컨트롤 정리는 각 15회였고 문맥 조립·회상은 모델이 필요했던
2회만 실행됐다. 새 탐색은 문맥 조립·회상 각 18회, 계획 준비·정리 각 19회였다.
빈 행동 보완 등 변경된 응답에 필요한 재검증을 생략하지 않은 결과다.

새 인출의 남은 문제도 화면·이벤트로 좁혔다. seq 341에서 hbl_no 입력이 이미 충족됐다고
판정해 생략했지만, 조회 후 캡처의 입력칸은 비어 있었다. 편찬 참조에는 번호가 들어 있어
조회 행 그룹의 pHash 거리가 8로 허용치 6을 넘었다. 크기는 1262×786으로 같고,
픽셀 차이는 조회 입력 텍스트 영역에만 있었다. 다음 상세 상단 화면은 해당 상세 그룹의
pHash와 같았지만 앞선 조회 행 그룹이 미전달 상태라 경로가 거기에 머물렀다.
따라서 두 번째 호출은 독립적인 화면 인식 실패가 아니라 앞선 경로 정체와 연결된다.
모델이 재조회 완료를 보고한 뒤 seq 384에서 경로가 재개됐고, 하단 완료 기억은 모델 호출
없이 결합됐다. 최종 seq 416의 verified와 post_save_verified는 모두 11개였다.

원본 탐색 seq 449와 편찬 그룹 a33ca5d4b5099213에는 조회 입력값이 명시적으로 빈 문자열이며
fill 계획도 보존돼 있었다. `memory_retrieval.py`의 `_restore_mapping`이 같은 노드의 이전
관찰 순번 4를 입력 전달 순번 3보다 최신이라고 판단해 빈 값을 덮었다. 이후 seq 333에서
그 값을 현재 관찰 순번 12로 다시 기록한 것이 입력 생략으로 이어졌다. 이 복원 함수는
137 제품 기준 `2defff9`부터 이번 `4fe62dc` 사이 변경되지 않았다. 같은 파일의 이번 변경은
소비자가 없는 pending response 대입 삭제뿐이다. 이는 이번에 발견한 기존 메모 우선순위
문제이며, 화면 유사도 임계값만 완화해 해결할 문제로 보지 않는다.

새 인출의 교육 완료 집합은 7개로 탐색의 8개보다 하나 적었다(`enter-record-fields` 없음).
제거된 스크롤 구간에 있던 완료 관찰과 관련 있을 가능성이 있으나 이번에는 인과 검증을
확장하지 않았다. ERP 저장 성공과 필드 메모 보존이 모든 교육 완료 기록의 동등성까지
뜻하지는 않는다.

저장 완료 알림과 재조회 상세의 상·하단 캡처를 직접 확인했다. DEMO HBL/MBL,
합성 거래처와 품명, 수량 12·단위 CT·중량 1250.5·컨테이너·출도착 항구가 보존됐다.
선택 사항인 품목 행이 비어 있는 것은 이 교육과 입력의 기대 결과다.

### 증거 위치와 판정 한계

로컬 protocol은 `.tools/memory-progress-138/protocol.json`이다. 비공개 캡처·원문·캐시는
커밋하지 않는다. 결과는 bench `evidence/runs/memory-progress-138-{fixed,cold,compilation,retrieval}`,
실행 원문과 프로파일·메모는 다음 core case에 보존했다.

- 기존 산출물: `cases/memory-progress-138-fixed/f59a25dd9375a349424c/case-6a8917bdda2140d2a938ac7ccf9d8dec/case`
- 새 탐색: `cases/memory-progress-138-cold/9aeb278bcdf0bf742ceb/case-8936a488e0f34c3faa95c23544cd34ea/case`
