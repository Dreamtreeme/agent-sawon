## 097 화면·행동·모델 원문 대조

실제 캡처에서 로그인 → 업무 메뉴 → House B/L 조회 전환을 확인했다. 조회 후 화면에는
번호 DEMO-HBL-001, 빈 결과 표, “조회 결과 0건”, “새 건 등록” 버튼이 함께 보였다.
로그인 가림이나 relay 입력 거절은 이번 실행에서 발생하지 않았다.

| 로그 seq | 확인한 사실 |
|---|---|
| 22·26·30 | 사용자명·비밀번호·로그인 클릭 전달 성공 |
| 42·56 | 모델이 업무 메뉴에서 조회 버튼 선택, 클릭 전달 성공 |

조회 클릭은 seq 84, 109, 133, 160, 184의 **5회 모두 전달 성공**이다. 여섯 번째 조회 계획은
중단되어 전달되지 않았다. 총 행동 전달은 로그인 3 + 메뉴 이동 1 + 번호 입력 1 + 조회 5 = 10.
신규 입력·저장·저장 후 상세 검토는 시작하지 못했다.

첫 재조회 선택(seq 96)부터 모델 요청에 다음 내용이 실제로 있었다.

- 직전에 전달한 fill/search의 종류, 출발 화면 query, 목적.
- OCR의 “조회 결과0건”, “새건등록”과 현재 이미지.
- 교육의 check-duplicate 완료 조건: 같은 번호 결과 행 또는 0건 표시.
- 바로 다음 open-new-record 교육: 0건이면 신규 버튼으로 등록 화면을 연다.

응답이 결과 건수 텍스트를 fields.value로 직접 반환했다. 따라서 OCR 미탐지, 교육 누락,
화면 좌표 전달 실패로 설명할 수 없다. 신규 행동을 모델이 제안했는데 코드가 거절한 사례도
아니다. 첫 반복 선택은 semantic_target_repeated 피드백이 생기기 전에 이미 발생했다.

## 원인의 확인 범위와 추상화

1. 관찰: 정상적으로 조회했지만 같은 조회 버튼을 반복했다.
2. 판단: 모델이 읽은 “0건”을 교육의 완료 조건에 연결하지 않고 조회를 미완료 행동으로 취급했다.
   “화면 변화가 없었다”는 이후 모델 설명은 결과가 0건인 정상 조회도 변화가 작을 수 있음을 놓친다.
3. 상태: 교육 초점 check-duplicate와 completed_step_ids=[]가 반복 요청에 남았다. 현재
   모델 응답은 필드 값 읽기와 다음 행동을 담지만, 이 응답에서 업무 단계 완료를 선언하지 않았다.
   숫자/문자 읽기와 업무상 완료 의미 연결은 별개의 문제임이 드러났다.
4. 한계: 단일 응답의 관찰을 메모에 먼저 반영하는 실행 순서는 모델이 그 관찰을 올바른 다음
   행동에 연결한다는 보장이 아니다. 이번 모델은 충분한 정보가 있어도 그 연결을 하지 못했다.

상태가 모델 판단을 얼마나 유도했는지, 이번 프롬프트 변경이 이전 성공 대비 실패율을 높였는지는
이 한 실행으로 확정할 수 없다. 반복 억제기가 최종 중단을 일으킨 것은 확인되지만, 이를 없애면
정상 신규 입력으로 진행한다는 근거는 없다. 첫 반복을 억제기 탓으로 돌리지 않는다.

## 검증 결론

전체 ERP 검증은 실패했다. 저장 상세에서 한 응답으로 확인·행동을 처리하는 변경의 무료 테스트와
095 기록 화면의 실제 모델 부분 재생 결과는 유지되지만, 097은 그 구간에 도달하지 못했으므로
해당 변경의 E2E 효과나 일반적인 루프 해소를 증명하지 못한다. 추가 제품 수정과 유료 반복 실행은
하지 않았다. 이 작업은 실행 및 문서 기록만이므로 전체 테스트를 반복하지 않고 문서 경로와
`git diff --check`를 확인했다.
