## 남은 문제 1: 잘못된 구조 기억과 현재 화면 의미의 충돌

두 실행 모두 seq92는 `새 건 등록`을 클릭하겠다고 하면서 `[403,728]`을 반환했다.
실제 화면에서 그 위치는 **닫기**다. 실제 신규 등록은 `[271,728]` 부근이다.
seq112는 원문 좌표 그대로 전달했고 다음 화면은 메인 메뉴였다. 이후 인출 메서드가
메뉴의 등록 버튼을 눌러 업무를 계속했다.

이 오라벨은 [139 조사](memory-value-reuse-erp-139-20261101.md)에 추적한 138 편찬물에
이미 존재하며 이번에도 같은 해시의 편찬물을 사용했다. 현재 OCR에는 두 버튼이 구별돼
있는데 모델 응답이 기억의 잘못된 이름·좌표를 다시 선택했다. 코드가 정확한 모델 좌표를
다른 좌표로 바꾼 사례는 아니다.

결국 조회창을 유지하는 직접 신규 등록보다 처음에 1행동, 저장 후 재조회에서 3행동이
더 필요해졌다. changed가 139의 26행동에서 140의 30행동으로 늘어난 차이에 대응한다.
작업 완료는 가능하지만 설명한 목표와 실제 화면 전환이 맞지 않았다. 화면 변화
`success=true`를 ‘신규 등록 화면 도착이 증명됐다’로 읽어서는 안 된다.

## 남은 문제 2: 정확한 클릭 point와 잘못 선언한 bbox의 충돌

changed seq326에서 모델 원문은 저장과 닫기의 bbox를 서로 바꿔 선언했다.

| 항목 | 첫 응답 seq326 | 재판단 seq350 | 실제 화면 |
|---|---|---|---|
| 닫기 bbox | `[32,875,112,49]` | `[154,878,104,41]` | 오른쪽 버튼 |
| 저장 bbox | `[149,873,113,51]` | `[36,878,104,41]` | 왼쪽 버튼 |
| 닫기 click point | `[206,898]` | `[206,898]` | 두 번 모두 닫기 안 |

`brain/graph/visual_points.py:VisualPointBindings.bind`는 클릭점이 선언된 대상 영역
안인지 검사한다. seq340–342에서 `visual_click_point_outside_target`으로 첫 계획 전체가
전달 전에 거절됐다. seq350은 클릭점을 그대로 두고 bbox만 바로잡았으며 seq364–365에서
실제로 한 번 닫았다. 거절된 계획을 실행한 것으로 세면 안 된다.

기하 검증 코드는 선언된 계약대로 동작했다. 그러나 실제 화면 기준으로는 올바른 point가
중복으로 기술된 잘못된 bbox 때문에 막힌 사례다. ‘모델 판단 전체가 틀렸다’나 ‘코드가
임의로 다른 버튼을 눌렀다’로 설명할 수 없다. bbox와 point 중 어느 관측을 실행 근거로
삼을지의 경계가 여전히 비용을 만든다. 이번 cleanup은 이 검증이나 프롬프트를 바꾸지 않았다.

첫 응답의 업무 상단 5값은 seq333에서 메모에 반영됐다. 행동이 거절됐다고 관찰도 버리지는
않았다. 이 사례는 이번에 고친 미선언 target의 KeyError 경로와는 다른 기존 기하 검증 경로다.

## 남은 문제 3: 이미 선택된 행에 단일 클릭 후 더블클릭

same seq413의 화면은 결과행이 이미 파란색으로 선택된 상태였다. 모델은 단일 클릭으로

더블클릭을 선택해 seq458에서 상세로 들어갔다. changed seq432는 바로 더블클릭했다.

이 때문에 same은 changed보다 실제 전달이 1개 많다. 139 same의 ‘이미 연 상세를
닫으려는 제안’은 이번에는 발생하지 않았고 상세 화면 진입 직후 바로 값을 확인했다.

## 판정 범위와 반증 조건

- 이번 코드 정리가 현재값 입력·관찰 누적·저장 후 증거·완료를 깨뜨렸다는 증거는 없다.
  업무값/화면/메모 연결은 두 실행에서 일치했다. 동시에 위 세 행동·계약 문제는 남았다.
- 미선언 대상 응답은 이번 두 실행에 없었다. 해당 수정의 실제 오류 처리 발동은
  증명하지 못했으며 기존 합성 회귀의 최초 응답·보완 응답 두 경로 검증에 한정된다.
- 같은 좌표의 source를 교정하는 응답, 코드 검토 모드, 다른 시드는 이번 실측 범위가 아니다.
  이 결과를 전 ERP·전 경로 검증이나 모델 오독률의 일반 추정으로 확대하지 않는다.
- 과거값이 새 관찰·입력으로 나타나거나, source/value가 변환 중 바뀌거나, 저장 전 entry가
  상세 확인 없이 saved_detail로 승격되면 기능 유지 판정은 반증된다.
- 정확했던 모델 bbox/point가 변환 후 뒤바뀐 증거가 나오면 이번 남은 문제의 원인 분류도
  다시 해야 한다. 현재는 오류가 원문에 이미 있고 변환·거절·복구가 그 원문과 대응한다.

제품 코드를 바꾸지 않은 검증이므로 전체 테스트를 중복 실행하지 않았다. 검증 대상 커밋의
검사 결과는 [cleanup 보고서](model-boundary-cleanup-20261101.md)의 762 passed,
2 xfailed 및 Ruff 통과다. 이번 보고서에는 경로·해시와 `git diff --check`를 확인했다.
