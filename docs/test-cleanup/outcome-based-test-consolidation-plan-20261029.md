# 실제 결함 검출력을 기준으로 한 테스트 통합 계획

## 출발점

제품 기준 커밋: `9defb83`. 이번 코드 정리와 ERP 결과는
[memory-runtime-incremental-20261029.md](memory-runtime-incremental-20261029.md)에 있다.
C2–C6/C1 정리를 끝낸 뒤 작성한 계획이며, 아래 대규모 테스트 통합은 아직 실행하지 않았다.

현행 전체 결과는 728 passed + 기존 3 xfailed, 42.13초(한 번 측정)다.
실제 ERP 9회는 정상 종료 7회, 실패 2회였다. 126은 입력 후 재확인 순환으로 저장하지 못했고,
132는 저장 10/10 후 재확인 순환으로 작업자가 종료했다. 테스트 전부 통과는 탐색 안정성의
증명이 아니다. 제품 함수로 기대값을 다시 계산하거나 내부 호출 순서를 고정하는 검증을
계속 늘리는 대신, 정보가 사용자 업무 결과까지 연결되는지를 기준으로 재편한다.

이번에 이미 적용한 테스트 정리:

- 제거된 구형 프롬프트로 fake 응답을 선택하던 분기를 삭제했다.
- 입력 후 다음 행동 테스트의 기대값은 제품 변환 결과 대신 원래 응답의 action/source/point다.
- 임시 타깃 생성에 의존한 공급자·계획 합성 fixture를 현재 경계에 맞게 수정했다.
- 제거된 bind_proposal의 직접 테스트를 compile_match의 실제 출력 검증으로 옮겼다.
- 중복 모델 evidence 테스트 두 함수를 저장 매핑 호환성의 두 입력 사례로 통합했다.

수집 사례 수는 731로 그대로다. 테스트 개수를 줄였다고 보고하지 않는다.

## 1. 삭제보다 먼저 대표 연결 검증을 선정

새 테스트를 먼저 대량 추가하지 않는다. 아래 기존 테스트에서 대표 경로를 선정하고,
누락된 실제 연결만 확장한다. fake는 공급자 응답·환경 입력 경계에 두고, 연결을 검증할
메모 갱신·계획 변환·실행 준비 함수는 실제 구현을 통과한다.

| 연결 | 현재 출발점 | 관찰해야 하는 결과 |
|---|---|---|
| 현재 화면 → 누적 메모 → 다음 요청 | test_observation_path_equivalence.py, test_screen_decision.py | 서로 다른 뷰를 거쳐도 source/value와 증거 범위가 유지되고 다음 요청에 전달된다. 같은 값의 다른 필드는 섞이지 않는다 |
| 교육 조회 → 빈 행동 보완/거절 복구 → 실행 | test_screen_decision.py의 synthetic 교육 확장 두 경로, test_replan_pipeline.py, test_plan_composition.py | 확장 상세와 현재 관찰이 보완 요청에 남고, 최종 action/source/point가 실제 전달된다 |
| 기억 산출물 → 현재 입력 재결합 → 실행 → 완료 | test_memory_retrieval.py, test_recorded_graph_replay.py | 새로운 입력값이 연결되고 이미 전달한 그룹을 반복하지 않는다. 예외 시 메모를 유지해 모델로 넘긴다 |
| 저장 결과 → 재조회 → 종료 | test_post_save_context.py, test_saved_evidence.py, test_recorded_graph_replay.py | 저장 성공과 작업자 종료를 구분하고, 재조회 중 얻은 사실을 다음 판단에 전달한다 |

126/132 기록은 `성공해야 한다`는 단언을 억지로 만들 자료가 아니다. 모델이 실제로 반복 행동을
반환했는데 fake를 성공 응답으로 바꾸면 실패를 은폐한다. 기록된 응답/프레임을 재생해 **메모가
유실됐는지, 다음 요청에 전달됐는지, 코드가 선택 행동을 바꿨는지**를 먼저 분리한다.
요청에 정보가 모두 있었는데 모델이 재확인만 선택했다면 그것은 모델 품질 평가 대상이며,
코드 단위 테스트를 추가하는 것으로 해결됐다고 하지 않는다. 유료 재평가는 별도 실행 계획으로 둔다.

## 2. 변이 검출표를 만든 뒤 삭제 판정

기존 테스트 실행에 한정한 monkeypatch 또는 격리된 checkout에서 아래 결함을 한 번에 하나씩
주입한다. 제품 변경으로 남기지 않는다. 준비 단계 오류/ImportError는 결함 검출로 세지 않는다.

| 결함 주입 | 실패해야 할 결과 단언 | 삭제 판단의 기준 |
|---|---|---|
| 모델 읽은 값의 메모 병합 한 번 누락 | 다음 요청의 해당 source/value 누락 | 같은 누락을 대표 연결 테스트와 국소 테스트가 모두 잡는지 |
| 조회한 교육 상세를 원래 prepared로 되돌림 | 빈 행동 보완/거절 복구 요청에 상세 단계 누락 | 일반·fallback이 같은 원인을 잡는지, 독립 경로인지 |
| 실행 ref를 다른 현재 컨트롤로 연결 | 실제 wire 대상/좌표가 원래 선택과 달라짐 | 정수→문자열 조립만 검사하는 국소 테스트를 대체할 수 있는지 |
| 현재 record 대신 편찬 당시 입력값 사용 | 인출된 실제 set_text 값이 새 입력과 다름 | 모델 없는 인출 대표 경로가 공급자/매핑 국소 검증까지 포괄하는지 |
| used 필터 또는 선행 그룹 조건 제거 | 전달 그룹 순서가 달라지거나 같은 행동 재선택 | C7 관련 세 테스트와 다른 기억 테스트의 검출 집합 비교 |
| 입력/관찰 순번 또는 저장 증거 범위 혼합 | 이전 입력 전달만으로 현재/저장 후 검증이 충족됨 | 순서 플래그 단언 대신 최종 보관·다음 요청으로 검증 가능한지 |

각 mutant마다 실패 nodeid와 실패 assertion을 표로 저장한다. 단순 line coverage 중복은 삭제
근거가 아니다. 유지되는 대표 테스트가 동일 결함을 감지하고 추가적인 동작 손실이 없을 때만
중복 테스트를 삭제한다. 서로 다른 결함을 잡으면 한 함수로 억지로 합치지 않는다.
변이 6종 자체도 완전한 결함 목록은 아니며 새 실제 실패가 발견되면 표에 추가한다.

## 3. 통합 대상과 우선순위

아래는 조사·통합 대상이지 전부 삭제 확정 목록이 아니다. 현재 조사 범위 7파일에는 test_
함수가 총 140개 있다. 전체 저장소 731사례의 개별 가치 감사를 완료했다는 뜻이 아니다.

| 우선순위 | 대상 | 구체적 조치 | 남길 경계 |
|---|---|---|---|
| 1 | test_replan_pipeline.py + test_plan_composition.py + screen_decision의 교육/보완 관련 테스트 | 일반·교육 확장·빈 행동·거절 복구·메서드 fallback을 공통 fixture의 시나리오로 정리. stages=[local,evidence,validate] 같은 내부 순서 단언을 최종 요청/응답/실행 단언으로 교체 | 보완 상세 누락, 잘못된 실행 대상, 복구 응답 자체가 잘못된 경우 |
| 2 | test_screen_decision.py의 의미 매핑·증거·타깃 관련 함수 | source가 있는 읽기, 출처 없는 관찰, 중복 라벨, 사라진 타깃을 대표 입력 행렬로 통합. 같은 local_payload를 기대값 생성에 재사용하지 않음 | 정확한 field/source/value, 실제 wire 좌표, 남겨야 할 완료 증거 |
| 3 | test_memory_retrieval.py의 분기·적응·그룹 전달 관련 함수 | C7 세 테스트를 포함해 변이 검출표 비교 후 중복만 제거. 새 입력 연결과 예외 인계는 대표 실행에 통합 | 선행 조건, 전달되지 않은 행동의 완료 오인, 현재 실행 메모 우선순위 |
| 4 | test_visual_proposal.py 및 screen_decision의 컴파일 관련 테스트 | 실제 실행 요청으로 검증이 겹치는 단위를 통합. 삭제한 중간 m문자열의 형식 테스트를 되살리지 않음 | 없는 현재 대상, 잘못된 스키마, 캡처 기하 변경 후 좌표 보존 |
| 5 | test_vocabulary.py | ScreenPlan/ScreenMatch의 동일 원문 fixture 중복 저장을 공통 fixture로 줄일 수 있는지 검토. 둘이 같다는 단언은 유지 | enum 값/순서, 공개 스키마의 의미와 의도된 변경 기록 |
| 6 | test_observation_path_equivalence.py의 3 xfail | 현행 계약과 실제 기록으로 여전히 결함인지 먼저 재분류. 고쳐서 pass, 폐기 계약이면 삭제, 미확인이면 별도 미해결 목록 | expected failure를 회귀 검출력이나 성공 건수에 포함하지 않음 |

별도 지원 설정을 사용하는 테스트는 현재 기본값이 아니라는 이유만으로 삭제하지 않는다.
R1–R3 옵션 폐기를 결정하지 않았으므로 `screen_matching=False` 등으로 실제 지원 경로를
검증하는 사례는 그 기능의 폐기와 함께 다룬다. 테스트에만 존재하는 가상 조합은 CLI/설정/
호출 경로를 대조한 후 보류 또는 삭제한다.

## 4. 비용을 줄이는 대상도 별도로 고른다

최종 시간 조사에서 가장 느린 테스트는 persistent_worker의 소유 자식 종료 확인 2.13초,
프로세스 동시 로그 쓰기 0.93초였다. 이들은 실제 프로세스 격리·로그 손실을 확인하므로
느리다는 이유로 fake로 바꾸지 않는다. 화면 메모 테스트 일부는 0.65–0.66초, 인출 메모
두 변형은 0.39–0.41초였다. 그래프 전체를 반복 만들 필요가 없는 입력 검증은 하위 계층으로
옮기되 메모·실행 연결의 대표 경로를 남긴다. 아직 묶음별 안전한 절감 시간은 미측정이다.
42.13초는 한 번의 값이므로 40초 이하 같은 목표를 이번에 임의로 약속하지 않는다.

## 5. 적용 단위와 완료 조건

1. 첫 묶음은 교육 확장/복구/계획 합성이다. 현재 코드에서 기준선과 대표 테스트를 확정한다.
2. 위 변이를 주입해 검출표를 확보한다. 어떤 테스트도 못 잡는 결함은 대표 연결 테스트에 보완한다.
3. 검출 집합과 동작 범위가 겹치는 테스트만 삭제/통합한다. fixture 공유 상태가 새지 않는지 확인한다.
4. 전체 테스트, statement/branch coverage, 표적 변이 검출표를 비교한다. 커버리지 0.5%p 이상
   하락 또는 기존에 검출한 변이를 놓치면 해당 묶음을 되돌리고 보류한다. 0.5%p 이내라도
   실제 동작 검증이 사라지면 허용하지 않는다.
5. 전후 전체 실행 3회의 중앙값과 테스트/fixture 코드량을 기록한다. 기존 실패는 별도 표시한다.
6. 묶음별 커밋 후 다음 묶음으로 넘어간다. 순수 테스트 변경마다 유료 ERP를 반복하지 않는다.
   제품 동작 변경이 없으므로 실제 ERP는 새 경계/가설을 확인할 필요가 있을 때 별도로 계획한다.

완료 보고에는 삭제된 nodeid → 남은 검출 테스트 → 실제로 잡는 mutant를 연결한다.
테스트 개수 감소 자체를 성공으로 삼지 않는다. 원래 테스트를 지우고 동일한 분기를 복제한
테스트를 새 이름으로 추가하는 방식도 통합으로 세지 않는다.
