## 수정 우선순위

### 1. 성공한 완료 근거를 행동 레시피와 함께 컴파일

성공 실행의 마지막 `operation=complete`가 만든 input key, 현재 OCR 라벨, 값 영역의 상대 관계와
완료조건 연결을 `completion_probe`로 저장한다. 새 건에서는 현재 입력값과 현재 화면에 다시 결합한다.
전부 일치할 때 기존 completion evidence를 생성하고, 불일치·모호함이 있으면 짧은 Luna 검증으로
돌아간다. 업무별 판정문을 코드에 쓰는 방식이 아니라 모델이 성공시킨 첫 선례의 검증 관계를
구조화하는 방식이다.

- 083 기준 정상 종료 예상: 약 47.5–48초
- 082 대비 예상 절감: 약 27초
- 모델이 다시 과거 단계로 돌아가며 쓴 39.6초의 실패 꼬리를 차단한다.

### 2. 로컬 시각 worker를 case가 아니라 하네스 수명으로 유지

현재 `PersistentWorker`는 한 Brain 프로세스에서만 유지되고 각 trial 종료 시 사라진다. OCR과
OmniParser를 relay/harness가 소유한 로컬 서비스로 옮기거나 동일 설정 worker pool을 사용한다.
가중치·device·버전이 바뀌면 새 worker를 만들고 실행 사이에는 입력 이미지 결과를 캐시하지 않는다.

- 실행당 예상 절감: 8–10초
- 이후 화면의 OCR/탐지는 이미 각각 약 0.18초/0.08초이므로 알고리즘 교체 우선순위는 낮다.

### 3. 같은 화면의 직접 입력을 relay batch로 실행

직접 fill 묶음은 모든 좌표와 캡처를 처음에 검증하고, 각 행동에서 허용 창·포커스·DPI를 재확인하되
중간 `_settle()` 전체 캡처를 생략한다. 묶음 끝에서만 안정화 캡처를 만들고 core가 모든 값을 다시
읽는다. 화면 경계를 넘는 click, dialog, select_option은 batch에 넣지 않는다.

- 현재 필드 입력13회: 7.27–8.06초
- 예상 절감: 5–7초
- 단순히 안전 대기 시간을 줄이지 않고 동일 화면 입력에 맞는 원자적 계약을 추가한다.

### 4. 신규 화면의 증거 target 보완 호출 제거

최초 ScreenMatch에서 evidence로 반환한 marker는 반드시 controls에 포함하도록 응답 계약을 좁힌다.
현재 행동에 필요하지 않은 과거 행 evidence는 action turn에서 제거하고, 필요한 누락만 보완한다.
레시피 miss인 새 화면에서 최초 판단+target-grounding의 이중 호출을 한 번으로 줄인다.

### 5. 프롬프트를 현재 단계 중심으로 축소

이미 사용한 method group 전체 대신 다음 그룹, 최근 결과, 현재 또는 다음 taught step만 보낸다.
최종 검증 fallback에는 현재 입력, 최종 완료조건, 현재 화면 근거만 제공한다. 083 최종 요청은
입력 12,749토큰이었으므로 절감 여지가 있지만, 호출 자체를 없애는 1번보다 우선순위가 낮다.

1–3번을 모두 적용한 반복 작업의 현실적인 목표는 **33–40초**다. 실제 수치는 각 변경을 분리한
동일 시드·새 값 A/B로 확인하며, 한 번에 여러 변경을 합쳐 절감 원인을 흐리지 않는다.

## 실행 직전 화면 갱신 우선순위 1단계

089 r1의 올바른 좌표가 폐기된 직접 원인은 실행 직전 캡처가 계획 캡처와 픽셀·크기·DPI까지
정확히 같아야 한다는 코어 조건이었다. 이제 정확히 같은 캡처는 기존 좌표를 즉시 사용하고, 픽셀이
달라지면 64비트 pHash로 같은 화면 계열인지 먼저 확인한다. 이미지 크기가 같으면 포커스 테두리,
캐럿, 입력값처럼 배치를 바꾸지 않는 변화로 보고 현재 캡처 ID에 기존 상대점을 결합한다. 크기가
바뀌면 새 캡처를 GPU OCR·로컬 컨트롤 탐지기로 읽어 역할·라벨 관계가 하나로 결합되는 현재 박스를
찾고, 명시 좌표가 있으면 박스 내부 상대 위치를 새 박스로 옮긴다. 이 경로는 의미 모델을 호출하지
않는다.

허용 프로세스와 창 핸들은 계속 일치해야 한다. pHash 거리가 설정 한도를 넘거나, 라벨이 없거나
중복되거나, 현재 컨트롤이 하나로 결정되지 않으면 행동을 보내지 않는다. 창 원점 이동·DPI 변화는
새 캡처 좌표계로 실행하며, 반응형 크기 변화는 오래된 좌표를 비례 확대하지 않고 새 로컬 박스에
다시 결합한다. 동일 화면의 연속 입력은 pHash 경로에서 OCR·탐지를 반복하지 않는다.

반응형 resize 입력 재결합, 텍스트 버튼 상대점 이동, 큰 장면 변화, 중복 라벨, 프로세스 교체,
창 이동과 연속 입력 회귀를 포함한 코어 전체 **885개 테스트**와 ruff check/format이 통과했다.
실제 ERP 파일럿과 시간 측정은 다음 단계에 남겨 두며 이 구현에는 신규 유료 호출이 없다.

## 성공 방법의 live 승격 우선순위 2단계

기존 `MethodRuntime`은 전체 업무 성공 뒤 후보를 case의 `methods-working.json`과
`method-candidate.json`에만 합쳤다. 다음 실행은 설정의 원본 파일을 다시 복사하므로, 082·084에서
완성한 후반 그룹과 완료 증거가 있어도 stage5 설정이 계속 불완전한081을 읽었다.

방법 설정에 선택적 `promotion_path`를 추가했다. 시작할 때 live 파일이 있으면 불변 seed보다 live를
우선하고, 없으면 seed로 시작한다. 전체 업무가 성공한 경우에만 case 작업 사본을 먼저 컴파일한 뒤
파일 잠금·원자 교체를 사용하는 `MethodLibrary.upsert`로 live revision을 올린다. 실패 실행은 live
파일을 만들거나 수정하지 않는다. case 후보도 실제 설치된 revision을 기록한다. 이 방식은 081·084
같은 과거 증거 파일을 덮어쓰지 않으면서 다음 실행이 최신 성공 방법을 자동 사용하게 한다.

다음 실제 실행용 stage6 설정은 완료 증거가 있는084를 seed로 사용하고 별도
`learned-procedure-live.json`을 승격 대상으로 둔다. 실패 미설치, 성공 revision2 설치, 다음 task의
live 우선 로드를 포함한 코어 전체 **888개 테스트**와 ruff check/format이 통과했다. 신규 유료
호출은 없고 실제 ERP 실행은 아직 하지 않았다.

## 로그인 구조 재사용 우선순위 3단계

기존 학습기는 action source가 `credential.*`이면 로그인 계획 전체를 버렸다. 그래서 업무 본문과
완료 증거를 전부 재생하는 웜 실행도 로그인 화면에서는 Luna에 필드와 버튼을 다시 물었다. 이제
로그인 그룹도 다른 화면과 같은 방법 계약으로 컴파일한다. 저장되는 것은 사용자명 입력·비밀번호
입력·로그인 버튼의 역할, 화면에 보이는 라벨 관계, 버튼 내부 상대점, 기대 결과와
`credential.username`·`credential.password` 소스 키다.

결합 단계에는 자격증명 값 대신 `[CREDENTIAL]` 존재 표지만 넘긴다. 실제 값은 기존처럼 실행 직전
`Brain.credentials`에서만 가져와 relay action에 넣고 로그에서는 가린다. 방법의 목적·기대 결과나
잘못된 anchor에 자격증명 문자열이 섞여도 성공 후보 컴파일 때 `{credential.*}`로 치환하거나 instance
anchor에서 제거한다. 실패한 전체 업무의 로그인 그룹은 live 라이브러리로 승격되지 않는다.

실제 자격증명 문자열을 일부러 목적·기대 결과에 포함한 테스트에서 후보 파일에 원문이 없고, 다음
화면 결합이 두 credential source와 로그인 click을 모델 호출 없이 복원함을 확인했다. 코어 전체
**889개 테스트**와 ruff check/format이 통과했다. 실제 ERP 웜 로그인 시간과 Luna0회 여부는 다음
파일럿에서 측정한다.

## 절차 순서·완료 증거 우선순위 수정

090은 ERP 필드10/10과 코어 완료에 성공해 로그인 그룹을 live revision3으로 승격했다. 그러나 기존
upsert가 새 그룹을 파일 끝에 추가해 로그인 그룹이 재조회·상세 이동 뒤에 저장됐다. 091은 로그인에서
Luna1회를 쓴 뒤 기존11개 그룹을 로컬로 실행해 ERP 저장은 성공했지만, 끝에 남은 로그인 그룹 때문에
학습된 completion을 검사하지 못했다. 상세 화면에서 Luna를 두 번 더 호출한 뒤 응답 검증
`ValueError`로 코어만 실패했다. 즉 ERP 입력 오류나 좌표 오류가 아니라 메서드 파일 삽입 순서를 실행
순서로 사용한 문제였다.

실행 그룹은 이제 사용자 절차의 `taught_step_id` 순서로 정렬하고, 같은 단계는 성공 전달 이력과 기존
순서를 보존한다. 전체 업무 성공 시에는 기존 그룹과 새 그룹을 합친 완전한 방법을 같은 순서로 만든
뒤 live에 저장한다. 절차가 없는 일반 적응 학습은 기존 순서를 유지한다. 과거 live 파일처럼 로그인
그룹이 뒤에 있어도 런타임이 로그인부터 결합하며, 모든 그룹을 전달한 다음 학습된 completion을 모델
호출보다 먼저 평가한다. 전달 로그의 purpose도 전체 방법명이 아니라 실제 현재 그룹 목적을 기록한다.

과거의 뒤집힌 live 순서 재현을 포함한 코어 전체 **889개 테스트**와 ruff check/format이 통과했다.
090 비용은$0.0016935, 091 비용은$0.00980165이며 둘 다 미확정0이다. 알려진 누적은
**$9.172441165**다. 091 실패는 분모에 보존하고 수정 후 별도 웜 실행으로 검증한다.
