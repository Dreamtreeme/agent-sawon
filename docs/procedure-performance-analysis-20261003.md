4회는 37.113초의 모델 지연과 약 39.580초의 경과 시간을 추가했다. ERP는 저장 성공이지만 코어는
`observation_error:ValueError`로 실패했다. 더 긴 행동 레시피만으로는 완료 판단을 안정화할 수 없다.

## 수정 우선순위

### 1. 성공한 완료 근거를 행동 레시피와 함께 컴파일

성공 실행의 마지막 `operation=complete`가 만든 input key, 현재 OCR 라벨, 값 영역의 상대 관계와
완료조건 연결을 `completion_probe`로 저장한다. 새 건에서는 현재 입력값과 현재 화면에 다시 결합한다.
전부 일치할 때 기존 completion evidence를 생성하고, 불일치·모호함이 있으면 짧은 Luna 검증으로
돌아간다. 업무별 판정문을 코드에 쓰는 방식이 아니라 모델이 성공시킨 첫 선례의 검증 관계를
구조화하는 방식이다.

- 083 기준 정상 종료 예상: 약 47.5–48초
- 082 대비 예상 절감: 약 27초
- 모델이 다시 과거 단계로 돌아가며 쓴 39.6초의 실패 꼬리를 차단한다.

### 2. 로컬 시각 worker를 case가 아니라 하네스 수명으로 유지

현재 `PersistentWorker`는 한 Brain 프로세스에서만 유지되고 각 trial 종료 시 사라진다. OCR과
OmniParser를 relay/harness가 소유한 로컬 서비스로 옮기거나 동일 설정 worker pool을 사용한다.
가중치·device·버전이 바뀌면 새 worker를 만들고 실행 사이에는 입력 이미지 결과를 캐시하지 않는다.

- 실행당 예상 절감: 8–10초
- 이후 화면의 OCR/탐지는 이미 각각 약 0.18초/0.08초이므로 알고리즘 교체 우선순위는 낮다.

### 3. 같은 화면의 직접 입력을 relay batch로 실행

직접 fill 묶음은 모든 좌표와 캡처를 처음에 검증하고, 각 행동에서 허용 창·포커스·DPI를 재확인하되
중간 `_settle()` 전체 캡처를 생략한다. 묶음 끝에서만 안정화 캡처를 만들고 core가 모든 값을 다시
읽는다. 화면 경계를 넘는 click, dialog, select_option은 batch에 넣지 않는다.

- 현재 필드 입력13회: 7.27–8.06초
- 예상 절감: 5–7초
- 단순히 안전 대기 시간을 줄이지 않고 동일 화면 입력에 맞는 원자적 계약을 추가한다.

### 4. 신규 화면의 증거 target 보완 호출 제거

최초 ScreenMatch에서 evidence로 반환한 marker는 반드시 controls에 포함하도록 응답 계약을 좁힌다.
현재 행동에 필요하지 않은 과거 행 evidence는 action turn에서 제거하고, 필요한 누락만 보완한다.
레시피 miss인 새 화면에서 최초 판단+target-grounding의 이중 호출을 한 번으로 줄인다.

### 5. 프롬프트를 현재 단계 중심으로 축소

이미 사용한 method group 전체 대신 다음 그룹, 최근 결과, 현재 또는 다음 taught step만 보낸다.
최종 검증 fallback에는 현재 입력, 최종 완료조건, 현재 화면 근거만 제공한다. 083 최종 요청은
입력 12,749토큰이었으므로 절감 여지가 있지만, 호출 자체를 없애는 1번보다 우선순위가 낮다.

1–3번을 모두 적용한 반복 작업의 현실적인 목표는 **33–40초**다. 실제 수치는 각 변경을 분리한
동일 시드·새 값 A/B로 확인하며, 한 번에 여러 변경을 합쳐 절감 원인을 흐리지 않는다.

## 단계별 적용 결과

1단계 완료 레시피를 적용한084는 전체48.012초/core41.967초에 성공했다. 최종 상세 화면의
현재 값11개를 모델 없이 결합했고 유료 Luna는 로그인1회만 남았다. 083의 잘못된 완료 판단 뒤
39.580초 꼬리가 없어졌다.

2단계는 인증된 loopback broker가 OCR·OmniParser worker를 matrix 수명 동안 소유하게 했다.
각 Brain은 새 이미지를 계속 추론하며 결과는 캐시하지 않는다. 브로커가 없으면 기존 case 내부
worker 경로를 사용한다. 086의 연속 두 trial은 모두 저장·재조회·상세10/10에 성공했다.

| 086 구간 | worker cold r1 | worker warm r2 | 변화 |
|---|---:|---:|---:|
| 첫 OCR+detector | 9.265초 | 0.466초 | -8.799초 (-94.97%) |
| OCR+detector 13화면 합계 | 14.219초 | 4.664초 | -9.555초 (-67.20%) |
| core 전체 | 42.357초 | 31.252초 | -11.105초 (-26.22%) |
| 하네스 전체 | 46.279초 | 35.395초 | -10.884초 (-23.52%) |

r2의 OCR PID5732와 detector PID39608은 r1과 같고 첫 요청부터 `model_initialized=false`였다.
유료 Luna 지연도 r1보다1.425초 짧았으므로 전체11.105초를 전부 worker 개선으로 세지 않는다.
worker 지표에서 직접 확인된 절감은9.555초다. 정상 종료 시 두 native worker와 임시 폴더를
정리하며, URL·토큰은 실행 환경에만 전달한다. 이 결과로 33–40초 목표의 상단을 달성했다.

3단계는 `fields` 검증을 사용하는 동일 캡처의 직접 `set_text` 묶음에만 적용했다. core가 한 번
갱신한 캡처로 모든 행동을 만들고 relay가 입력 전에 모든 좌표를 검사한다. 실행 중에는 각 입력마다
allowlist 창, 포커스, DPI와 point hit를 다시 확인하고, 마지막 입력 뒤에만 `_settle()`을 수행한다.
로그인, click, dialog, 선택 동작과 화면 경계를 넘는 계획은 기존 단건 실행기를 사용한다. 부분 실패는
실제로 전달된 앞부분만 `unchecked` transition으로 남기고 이후 입력을 중단한다.

계약·릴레이·코어 전체 검사는 통과했다(core878, bench577·GUI6 제외). 실제087은 첫 관찰에서
전체 화면 외부 앱이 전경인 상태였고 Windows가 ERP `SetForegroundWindow`를 거부해 입력·모델
호출 전에 중단됐다. r2는 환경 불안정 규칙으로 실행 전 취소됐으며 비용은0이다. 사용 중인 앱을
강제로 가리지 않았으므로 3단계의 실제 시간 절감은 아직 측정하지 않았다. 누적 추정은
$9.108858215, 미확정0으로 유지한다.

4단계는 행동 응답의 `evidence`가 현재 `controls`에 정의하지 않은 부수적인 과거 행 marker를
가리킬 때 그 근거를 행동 실행 근거로 취급하지 않도록 바꿨다. 현재 행동 target, 미완료 입력의
필수 검증, 완료·중복 증거는 기존처럼 반드시 현재 controls에 결합해야 한다. 따라서 실행에 필요하지
않은 행 정보 때문에 전체 화면 의미를 다시 묻지 않으면서 실제 행동 target 누락의 보완 경로는
그대로 남는다.

실제088은 저장·재조회·상세10/10에 성공했다. 082에서 두 번 발생한
`action_targets_grounded`가 0회가 되었고 해당 보완 호출14.339초/$0.00460085가 사라졌다.
Luna 총호출은6→5회였다. 두 번째 신규 화면에서 모델이 `needs_image`를 선택해 이미지 재판단1회
9.283초/$0.00413670이 별도로 발생했으므로 전체 모델 시간·비용 절감은 각각의 호출 목적을 나눠
본다. 088 전체94.101초/core89.579초는 첫 로컬 worker 기동12.771초와 Luna 지연 변동을 포함해
086 worker-warm r2와 직접 성능 비교하지 않는다.

088에서 11개 직접 입력 batch는2.470초였다. 082의 같은 11개 단건 입력 합6.184초보다3.714초
(60.1%) 줄어 3단계의 실제 효과도 함께 확인했다. 최초 하네스 결과가 미확정 비용으로 표시된 원인은
모델 사용량이 아니라 `batch_returned` 집계 미지원이었다. 원본241개 이벤트는 전부 유효했고 오프라인
재집계는 Luna5·local13, 비용$0.018007, 미확정0이다. 벤치 집계기가 배치 요약을 검증하되 개별 행동을
중복 계수하지 않도록 수정했다.
