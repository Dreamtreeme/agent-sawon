# 추상화 누수와 결합도 점검

## 재현하고 수정한 문제

| 경계 | 원인과 영향 | 수정 | 검증 |
|---|---|---|---|
| 노드 입력 상태 → Brain | `copy_worker_state`가 바깥 컨테이너만 복사했다. ActionPlan.audit, PendingAction, 중첩 관찰 데이터가 이전 노드와 공유됐다. | 데이터 스냅샷 전체를 deepcopy한다. 같은 스냅샷 내부의 별칭·순환 참조는 유지한다. | 중첩 audit 수정이 원본에 전파되는 실패를 먼저 재현하고 수정 후 통과했다. |
| Brain → 노드 반환 상태 | 반환 객체를 `_worker_state`에 그대로 넣어 외부의 상태 수정이 Brain을 변경했다. | 내부 route를 갱신하고 분리된 스냅샷을 반환한다. | 반환된 lifecycle과 중첩 rolling_turns 수정이 내부 상태에 전파되지 않는다. |
| 비용 예약 → 공급자 생성 | budget이 factory의 설정 클래스를 import하고 패키지 초기화가 Gemini SDK를 즉시 로드했다. 공급자 생성과 순수 비용 계산이 연결돼 있었다. | 설정 계약을 models.settings에 두고 SDK는 해당 공급자 생성 시에만 로드한다. 기존 공개 GeminiClient import는 지연 로드로 유지한다. | 별도 Python 프로세스에서 실제 Luna 설정의 CallBudget을 읽은 후에도 openai/google.genai가 sys.modules에 없음을 확인했다. |
| 그래프 조립 → 구체 Brain | 그래프 조립에 네 노드만 필요한데 타입 계약이 Brain 전체였다. | WorkerNodes Protocol에 네 상태 변환만 명시한다. | 실제 Brain 및 기존 WorkerStub 그래프 조립 테스트를 사용한다. |

추가 방어 분기나 행동 차단은 넣지 않았다. 모델에 전달하는 목표·선택 방식, 실행 정책,
모델 비용 한도도 바꾸지 않았다. 모델 SDK 로드 분리는 네트워크 요청이 아니다.

## 상태 복사 비용

합성 UI 요소 500개를 가진 관찰 상태를 100회 복사한 로컬 측정에서 중앙값은
2.843ms, 최대는 3.034ms였다. 한 노드의 입력·출력에서 각각 복사하므로 이 크기의
상태에서 복사 두 번은 대략 5.7ms다. 실제 ERP 전체 지연이나 대형 실행 기록의
상한을 측정한 결과는 아니다. 스냅샷에 SDK, relay, 열린 파일 같은 서비스 객체를
추가해서는 안 된다.

## 여전히 남아 있는 결합

- `execution.py`는 Brain의 사설 메서드로 재조정·정책 검사·실행·결과 기록을 수행한다.
  Protocol에 기존 메서드를 전부 옮기기만 해서는 해결되지 않는다. 실행 요청에 필요한
  관찰·정책·예산을 확정하고, 실행 결과를 반환해 Brain이 상태를 반영하는 구조가 필요하다.
- `MethodRuntime`은 Brain 전체를 보관하며 task, 입력값, credentials, observation, log를
  읽는다. 업무 방법 선택용 데이터와 기록용 의존성을 좁혀야 한다. 자격증명 값이 학습
  자료에 들어가지 않는 현재 검사를 유지하면서 호출별 입력 계약으로 바꾸는 후속 범위다.
- WorkerState는 아직 Brain의 전체 런타임 상태가 아니다. verified, saved_evidence,
  method history 등은 밖에 남아 있다. 이번 변경은 인계 데이터의 소유권을 바로잡은
  것이며, 그래프 스냅샷만으로 중단·재개를 완전히 지원한다는 의미가 아니다.

따라서 파일 분리가 끝났다는 이유로 전체 아키텍처가 독립됐다고 판단하지 않는다.
실행기와 방법 재사용기의 전면 분리는 이번 수정의 완료 범위가 아니다.
