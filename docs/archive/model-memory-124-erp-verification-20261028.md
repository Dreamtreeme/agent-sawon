# 124 — 모델 누적 메모를 사용하는 기억 인출의 실제 ERP 검증

## 결과

시드 1에서 탐색 → 편찬 → 기억 인출을 각각 1회 실행했다. 탐색과 인출 모두 독립 ERP 채점
10/10, 작업자 exit 0이었다. 인출은 편찬된 11개 행동 그룹과 완료 매핑을 사용했으며 원격 모델
호출, 모델 복구, 화면 캐시 선택이 모두 0회였다. 실행 중 제품 코드·설정·프롬프트는 변경하지 않았다.

| 구간 | ERP / 종료 | 작업자 시간 | 원격 모델 호출 | 로컬 탐지 호출 | 전달 행동 | API 비용 |
|---|---|---:|---:|---:|---:|---:|
| 새 탐색 | 10/10 / exit 0 | 142.103초 | 16 | 13 | 26 | $0.0327732 |
| 기억 편찬 | 성공, 첫 시도 | 모델 응답 18.217초 | 1 | 0 | 해당 없음 | $0.0034822 |
| 기억 인출 | 10/10 / exit 0 | 26.917초 | **0** | **0** | 24 | **$0** |

전체 API 비용은 **$0.0362554**, 미확정 비용 호출은 0건이다. 편찬 시간은 모델 응답 지연으로,
작업자 실행 시간과 집계 범위가 다르다. 하네스 전체 시간은 탐색 145.529초, 인출 30.288초였다.
OCR은 인출에서도 실행했다. 로컬 탐지 0회는 OmniParser 모델 호출 건수이며 OCR 생략을 뜻하지 않는다.

품명이 잘린 프레임의 OCR은 이번에도 `Syiueuie`(0.45636), `Sampe pa`(0.63874)였다.
기억의 `{"source": "description"}`을 현재 record와 연결했으므로 메모는 이 OCR로 바뀌지 않았다.
123에서 발생한 `delivered_value_not_observed`와 해당 모델 재호출은 이번에 발생하지 않았다.

입력 전달과 확인값은 구분했다. 예를 들어 등록 화면 상단 HBL은 하단으로 이동한 뒤에도
마지막 빈칸 관찰과 `delivery.value=DEMO-HBL-001`을 함께 보관했다. 해당 화면을 다시 읽었다고
임의로 기록한 것이 아니다. 재조회한 수정 화면에서는 편찬된 상세 매핑을 복원해 별도 노드의
saved_detail 값으로 연결했다. 이 인출값은 새 모델 판독이 아니라 탐색에서 배운 모델 해석의
재사용이며, 이번 저장 결과의 정확성은 캡처 직접 확인과 독립 ERP 채점으로 별도 확인했다.

## 기억 인출 경로

- `method_bound`: 11회, 원본 reuse 그룹 전달 11/11.
- `method_completion_bound`: 1회(seq 333).
- `screen_similarity`: 12회 모두 memory_retrieval.
- `memory_retrieval_exception`, `method_fallback`, `screen_match_rejected`, `screen_memory_fallback`: 각 0회.
- 화면 캐시 선택: 0회. adaptation 및 learned 전달: 0회.
- 재현 정의 v2: 캐시 허용·비허용 모두 true. 모든 그룹 전달도 true.
- 메모 스냅샷: 12회. 등록·조회·수정 등 화면 노드별 저장이 유지됐다.
