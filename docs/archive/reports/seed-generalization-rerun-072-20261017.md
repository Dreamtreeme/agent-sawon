## 결과

시드 0·1·2 콜드는 모두 작업자 성공 및 ERP 10/10이었다. 웜까지 성공한 것은 시드 0이다.

## 고정한 조건

- 모델: `config/models.toml`의 Anthropic `claude-haiku-5-5`, low, 출력 한도 8192.
- 교육: bench의 `education/development/company-000.json`, `company-001.json`,
  `company-002.json`. 각 파일의 해시를 프로토콜에 보존했다.
- 콜드: 시드별 새 case, 빈 메서드·화면 캐시.
- 웜: 해당 시드의 성공한 콜드 기록을 Critic 편찬하고 해당 콜드 화면 캐시를 복사.
  다른 회사의 메서드는 섞지 않았다. ERP는 새 하네스 trial에서 시작했다.
- visual-only, GPU 탐지/OCR, `guard_mode=observe_only`, 동일 실행 프로필.
- 프로덕션 코드·모델 설정을 실행 도중 수정하지 않았다. 시작 프로토콜의 코어 소스
  해시와 종료 시 파일을 대조해 차이가 없음을 확인했다.
- 모델 판단에는 relay 관찰만 전달했다. 표의 ERP 점수는 실행 후 하네스 채점이다.

## 시드 0: 성공했지만 순수 메서드 재생은 아님

웜 시간은 121.552→64.230초, 유료 호출은 15→6으로 줄었다. 로그에는 화면 캐시 적중
8회가 있다. 최초 편찬 로그인 그룹은 `screen_changed` 거절로 interrupted가 되었고,
모델 복구 후 나머지 진행에 화면 캐시가 사용됐다. 따라서 이 성공은 편찬 그래프만으로
모든 행동을 무호출 재생했다는 증거가 아니다.

콜드·웜 최종 캡처를 직접 확인했다. 두 실행 모두 저장 번호 1이 표시된 상세 화면에서
추가 정보의 입력값이 보인다.

## 시드 1: 로그인 좌표 선택 이후 relay가 거절

웜 `run_log.jsonl`의 순서:

1. seq 17–22: 캐시 좌표로 계정·비밀번호 입력이 전달됨(`ok=true`).
2. seq 24: 코어가 캡처를 갱신하고 `phash_same_layout`으로 좌표를 연결함.
3. seq 25–26: 로그인 버튼 `(228, 246)` 클릭 요청을 relay가 `screen_changed`로 거절.
4. seq 35: 모델 1회가 로그인 재시도를 제안.
5. seq 47–48: 계정 재입력 전달 성공.
6. seq 50–52: 코어 연결은 pHash 거리 0이지만 비밀번호 입력 요청은 다시
   `screen_changed`로 거절.
7. seq 54–55: 진전 없는 단계 실패 2회가 누적되어 `repeated_phase_failure:task` 종료.

캡처 `visual/e3623ad8-7869-4260-912e-4cdf7e200885/capture.png`를 직접 확인했다.
계정과 마스킹된 비밀번호가 입력되어 있고, 요청된 로그인 좌표는 보이는 로그인 버튼
안에 있다. 계정 정보를 몰랐거나 로그인 버튼 좌표를 못 찾았다는 설명은 이 기록과 맞지 않는다.

`../agent-sawon-bench/relay/service.py:675`의 `_visual_fresh()`는 실행 직전 다시 캡처해
content hash의 정확한 일치를 검사하고, 다르면 입력 전에 거절한다. 코어의 pHash 기반
연결 성공과 relay의 정확한 content hash 일치 검사는 서로 다른 판정이다.
현재 기록은 이 경계에서의 거절을 입증한다. 거절 시 새로 캡처한 비교 이미지가 별도로
저장되지 않아, 어느 픽셀이 바뀌었는지나 caret만이 원인인지는 확정할 수 없다.

## 시드 2: 보조 앵커 개수 때문에 편찬 전체 거절

콜드 화면 작업은 성공했다. 편찬 모델의 응답에서 다섯 번째 그룹 `c006`의
`context_anchors`가 9개였다. `brain/demo_learning/warm_methods.py:36`의 로컬 계약은
최대 8개이므로 `groups[4].context_anchors: too_long`으로 응답 전체가 거절됐다.

원래 로컬 스키마의 `maxItems: 8`은 공급자 요청에서 구조적 제한이 아닌
`description: "{maxItems: 8}"`으로 변환되어 있었다. 모델은 이를 초과했고, 응답 후
Pydantic 검증에서 중단됐다. 오류 사용량은 공급자가 반환하여 비용은 확정돼 있다.

추가 API 없이 응답 복사본의 앵커만 8개로 줄여 `compile_warm_method()`를 메모리에서
실행하자 10개 그룹이 편찬됐다. 이는 이번 직접 중단 원인이 초과 앵커임을 뒷받침한다.
그 결과를 파일로 저장하거나 웜 실행에 사용하지는 않았다. 실제 웜 성공 여부는 미측정이다.

## 기록용 실행기의 오류와 실제 실행 순서

첫 시드 0 편찬은 원문 추적 실행기의 `runpy` 모듈 네임스페이스 때문에
`WarmMethodAssembly`의 `WarmGroupSelection` 참조를 해석하지 못했다.
`PydanticUserError`, 모델 호출 0, 비용 0이었다. 오프라인 스키마 생성으로 재현했고,
실행기를 정상 모듈 import 후 `main()` 호출로 고쳤다. 제품 코드는 바꾸지 않았다.

기존 드라이버가 이미 다음 시드를 진행했으므로 실제 순서는 다음과 같다:

`0 콜드 → 0 편찬 실행기 오류 → 1 콜드 → 1 편찬 → 1 웜 → 0 편찬 보완 → 0 웜 → 2 콜드 → 2 편찬 실패 → 종료`.

원래 오류 산출물은 `seed-000/compilation`, 정상 재개 산출물은
`seed-000/compilation-trace-fixed`로 보존했다. 상태 파일의 `compilation_attempts`에
실행기 오류를 별도 분류했다. 제품 실패 시드는 1이며, 그 다음 시드 2까지의 중단 규칙을
적용했다. 시드 1의 실패를 재시도로 교체하지 않았다.

- 편찬 원문: 각 편찬 디렉터리의 `model-requests/trace.md`.
- 53개 유료 요청 모두 요청 fingerprint, SDK 텍스트, 이미지 바이트, 공급자 응답 보존을
  대조했다. 오류 응답인 시드 2 편찬도 포함한다.
- 시드 0 콜드·웜, 시드 1 콜드·실패 웜, 시드 2 콜드의 관련 캡처를 직접 열어 확인했다.
- 프로덕션·테스트 코드는 변경하지 않아 전체 pytest는 재실행하지 않았다.
  문서 경로와 `git diff --check`를 확인했다. 원본 화면·로그·캐시는 커밋하지 않았다.

콜드의 입력·저장·재조회 흐름은 서로 다른 세 레이아웃에서 성공했다. 반면 웜의
relay 신선도 검사와 편찬 메타데이터 처리에는 별도 문제가 남아 있다. 이번 결과만으로
전체 시드나 웜 일반화가 완료됐다고 판단하지 않는다.
