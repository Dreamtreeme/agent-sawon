# 124 실행의 코드·메모·기록 회고

## 범위와 결론

제품 코드 `3d5831d`와 보고서 `b43e54b` 상태에서 124 탐색·기억 인출 기록을 조사했다.
124는 탐색·인출 모두 ERP 10/10, 정상 종료였고 인출은 원격 모델 0회, 26.917초였다.
이 성공을 뒤집는 조사가 아니라, 정상 경로에서 숨겨진 손실과 예외 경로의 남은 결함을
분리하는 조사다. 제품 코드, 설정, 과거 실행 기록은 변경하지 않았다. 새 ERP·API 호출도 없다.

가장 중요한 문제는 메모를 재사용하는 것 자체가 아니다. **모델이 읽은 사실 중 일부는 저장에서
빠지고, 보존된 사실은 인출할 때 새 관찰처럼 기록되며, 같은 행동도 응답 설명이 달라지면
별도의 대체 행동으로 관리된다.** 이 경계가 불필요한 처리와 잘못된 진단을 만든다.

## 1. 입력 키가 없는 사실은 모델이 읽어도 화면 트리에 남지 않는다

`brain/graph/screen_memory.py:36`은 업무 입력 키에 연결된 대상을 `fields`, 나머지를
`controls`에 둔다. `:45`의 값 저장 조건은 다시 `field.source in values`를 요구한다.
따라서 버튼뿐 아니라 결과 건수·저장 메시지·저장 번호도 이름·role·bbox만 남는다.
`recall_screen_tree()`의 `:100`은 controls를 role만으로 투영한다.

| 탐색 계획 seq → 메모 seq | 모델이 읽은 사실 | 노드에 실제 남은 내용 |
|---|---|---|
| 106 → 110 | 조회 결과 0건 | label, role, bbox, observation_id |
| 340 → 343 | 저장 완료 안내의 업무 식별자 | 같은 네 항목 |
| 340 → 343 | 저장 번호 1 | 같은 네 항목 |
| 340 → 343 | 저장 완료·적하목록 미전송 안내 | 같은 네 항목 |
| 368 → 371 | 작성자·저장 번호·saved 안내 | 같은 네 항목 |
| 395 → 398 | 조회 결과 1건 | 같은 네 항목 |

13건은 판독 발생 건수이며 모두 중요한 업무 증거라는 뜻은 아니다. 제목 같은 항목도 포함한다.
원문 로그와 일부 설명·진행 상태에는 흔적이 남으므로 모든 기록에서 사라졌다고 할 수는 없다.
`engine.py:535`의 교육 완료 누적도 완료한 단계 ID를 보존하지만 결과 문장 자체를 저장하지는 않는다.
문제는 다음 판단이 읽는 구조화된 화면 트리에서 이 사실을 다시 꺼낼 수 없다는 점이다.
이번에는 실패하지 않았으나 예외 복구 시 같은 내용을 다시 확인하게 만들 가능성이 있다.

입력 여부로 사실 보존을 제한하는 조건을 정리하는 것이 후보이며, OCR 재해석이나 새로운
모델 호출을 추가할 이유는 없다. 화면 노드의 기존 값 보관·투영 경로를 함께 다루어야 한다.

## 2. 예외 처리 뒤 이미 대체한 행동이 후보로 남는다

`brain/graph/memory_retrieval.py:351`은 미검토 대체 행동의 `replaced_edge`를 읽는다.
`:372`의 remaining은 `used`만 제외한다. 반면 `:386`은 replaced_edge를 다음 행동의
선행 조건 충족으로 인정한다. 원래 행동을 후보에서 빼는 시점은 `verify_delivery()`의
`:843`이므로, 그 전에 같은 화면에서 원래 행동과 다음 행동이 둘 다 결합될 수 있다.
`:460`은 후보가 정확히 하나가 아니면 인출을 포기한다.

123 seq 205의 화면·편찬물·요청 입력으로 현재 함수를 읽기 전용 재생했다.

| 격리된 재생 상태 | 결합 가능한 후보 | 결과 |
|---|---|---|
| 원래 기록에 따른 대체 대기 상태 | 하단 6칸 입력 + 다음 스크롤 | 후보 2개, 선택 없음 |
| 원래 행동만 소비한 것으로 표시한 반사실 상태 | 다음 스크롤 | 후보 1개, 선택 성공 |

반사실 상태는 원인 분리를 위한 진단이며 제품에 즉시 같은 변경을 하자는 뜻은 아니다.
효과 확인 전에 영구 완료로 만들지 않고도 대체 중인 원래 행동의 재선택을 제외할 수 있는지
기존 선택·검토 순서에서 해결해야 한다. 새 차단 정책을 추가할 사안이 아니다.

`tests/test_memory_retrieval.py:1337`의 기존 회귀 테스트는 다음 화면의 해시를
`first.screen_phash ^ 1023`으로 바꾼다. 대체 효과 확인의 성공·실패는 검사하지만,
같은 화면에서 두 후보가 동시에 결합되는 상황은 검사하지 않는다. 테스트 삭제 근거는 아니다.
124는 adaptation 없이 끝났으므로 이 결함이 해소됐다는 증거가 되지 않는다.

## 3. 기억 인출이 새 관찰로 재기록되고, 자기 비교가 값 검증처럼 보인다

현재 호출 순서는 다음과 같다.

```text
편찬 field_values + 이번 실행의 메모
  → memory_retrieval._restore_mapping()
  → ScreenMapping
  → engine._remember_model_task_evidence()
  → remember_screen(): 현재 관찰 ID·순번으로 last_observation 기록
  → _record_model_evidence(): verified / 저장 후 증거 갱신
```

인출값을 공통 실행 경로에서 사용하는 것은 합의한 동작이다. 하지만 이 경로는 기억 인출과
이번 프레임의 모델 판독을 구분하지 않는다. 124 원격 호출 0회인 인출 기록에 다음이 남았다.

- `select.decision`의 `source=model`: 7건 (`engine.py:1806`의 고정 값).
- `screen_node_selected.source=model_mapping`: 12건.
- `model_task_evidence_recorded.reviewer=screen_model`: 7건.
- 인출한 매핑을 노드에 반영한 메모 스냅샷: 12건.

이는 명칭 문제에 그치지 않는다. `last_observation`의 새 순번은
`pending_screen_inputs()`에서 입력 이후 확인 여부를 계산할 때, `_restore_mapping()`에서
어느 값이 더 최근인지 고를 때 사용된다. 인출했다는 이유로 관찰 시점이 새로워진다.
다만 인출 매핑에 없는 필드까지 모두 갱신되는 것은 아니다. 124 하단 화면에서 상단 HBL의
이전 빈칸 관찰과 전달 이력이 유지된 것은 정상적으로 확인했다.

`brain/cache/methods.py:1035`의 완료 결합 함수는 주석에 현재 보이는 업무 값을 검증한다고
적혀 있다. 실제로는 `{"source": key}`를 현재 입력값으로 치환한 뒤 `field_matches()`로
같은 현재 입력값과 비교한다. 참조 값에 대해서는 독립적인 값 확인이 추가되지 않는다.

이를 구분하기 위해 저장된 최종 화면은 수량 12 그대로 두고 입력 record의 수량만 999로 바꿔
완료 결합 함수에 전달했다. 결합은 성공했다. **완료 결합 함수가 새 시각 판독기가 아니라는
증명이며, 전체 작업자가 이 조건에서 잘못 성공한다는 증명은 아니다.** 124 실제 화면과 독립
ERP 채점은 올바른 값 12를 확인했다.

기억을 버리거나 매번 모델·OCR로 재검증하는 처방은 이 조사에서 도출되지 않는다. 기존 기억의
출처·관찰 시점을 유지하고, 인출·전달·새 관찰의 의미를 일치시키는 것이 정리 범위다.
특히 자기 비교와 오해를 부르는 검증 명칭은 별도 보증처럼 남겨 두지 않아야 한다.

## 4. 실행과 무관한 응답 차이가 행동 대체 관리로 들어간다

`brain/graph/screen_decision.py:2203`은 `response != method_proposal`이면 `remember()`를
호출한다. 비교 대상은 행동뿐 아니라 설명 등 응답 전체다.
124 첫 화면의 결합 응답에서 purpose 뒤에 공백 하나만 추가한 합성 재생 결과:

```text
steps_equal = True
response_equal = False
pending.origin = adaptation
pending.replaced_edge = 원래 그룹
```

`remember()` 내부에서는 실제 행동이 같은지 다시 비교해서 대체 관계를 만든다. 설명 차이가
새 행동 학습 대기 상태로 들어온 뒤 또 행동 동일성을 비교하는 구조다. 이 상태는 2번의
후보 관리 문제와 연결될 수 있다. 124 실제 실행에서 이 합성 변형이 발생한 것은 아니다.
정리 대상은 설명을 버리는 것이 아니라 설명 갱신과 실행 경로 대체를 같은 사건으로 취급하는 부분이다.

## 5. 새 입력 참조와 과거 업무 문자열이 함께 인출된다

`remembered_field_values()` (`brain/cache/methods.py:171`)는 명시적 source가 있는 판독값만
입력 키 참조로 바꾼다. 그 외 값은 문자열로 보존한다. 124 편찬물의 그룹 index 7과 9에는
저장 안내·조회 결과의 이전 HBL이 문자열로 남아 있었다.

합성 새 record의 HBL을 `SYNTHETIC-NEW-HBL`로 연결해도 이 두 문자열은 이전 HBL 그대로였다.
입력칸의 참조는 새 값으로 바뀌므로 같은 기억 안에서 서로 다른 업무 식별자가 공존할 수 있다.
`retrieve_screen_memory()`의 procedure에는 이 field_values도 들어가 예외 시 모델에 전달될 수 있다.
이번에는 같은 record를 재실행했고 모델 복구도 없었으므로 실제 충돌은 관찰하지 않았다.

과거 판독 문자열을 보관한 것은 올바르지만, 그것을 현재 사실로 전달하는 것은 다른 문제다.
문자열이 비슷하다는 이유로 전부 치환하면 저장 번호 등에도 오적용될 수 있다. 편찬 시 보존할
역사적 관찰과 새 입력에 연결할 참조를 구분하는 범위를 먼저 정해야 한다.

## 6. 모델을 호출하지 않아도 호출용 문장을 모두 만든다

`build_decision_prompt()` (`screen_decision.py:1473`)가 상태·계약·메서드 문맥을 모으고
전체 규칙과 JSON 문자열까지 조립한 다음 `select_screen_response()`로 간다.
124 인출에서 원격 모델은 0회였지만 프롬프트는 12회, 합계 391,111자를 만들었다.
각각 21,273–41,442자다. 로그의 상태 JSON 크기 합계 305,105 bytes는 별도 지표이므로
문자 수와 합산하지 않는다. 탐색의 프롬프트는 실제 호출에 쓰였으므로 낭비로 세지 않았다.

인출·검증에 필요한 상태와 계약은 유지하고, 원격 호출용 문자열 생성만 지연할 수 있다.
이 문자열은 전송되지 않았으므로 API 비용은 없었다. 조립 CPU 시간은 계측하지 않았으며
이 변경만으로 실행 시간이 크게 줄어든다고 주장할 근거는 없다.

## 7. 작지만 확실한 정리 후보

- `MethodLibrary.methods()` (`methods.py:828`)는 호출마다 같은 파일을 읽고 Pydantic으로
  파싱한다. 124의 12개 화면에 대해 기억 검색 → 문맥 → 패턴 선택 부분 경로를 재생하니
  화면당 4회, 총 48회 읽었다. 파일은 83,477 bytes다. 별도 합성 검사 2회를 포함한 50회
  읽기·파싱 시간은 한 번의 측정에서 약 31ms였다. 실제 ERP 전체 호출 횟수를 계측한 값은
  아니며 주요 병목도 아니다. 같은 관찰 안에서 파싱 결과를 공유하되 upsert를 반영하는 정도가 적절하다.
- `match_pattern()`의 `elif taught_replay`와 `else`는 둘 다 `groups = remaining`이다.
  바로 아래 used 검사도 remaining 생성에서 한 검사와 겹친다. 후보 순회 중 used가 바뀌는지
  확인한 뒤 제거할 수 있는 작은 중복이며, 이번 실패의 원인은 아니다.
- 편찬의 의미 이름 → 내부 대상 번호 → `_restore_mapping()`의 이름 → `local_payload()`의
  내부 번호 변환이 있다. 공용 실행기의 번호 계약은 필요하지만 인출 매핑을 구성하기 전의
  왕복은 통합 후보다. 순서·참조 테스트를 먼저 대조해야 하며 이번에는 삭제 가능하다고 확정하지 않았다.

`exact_capture` 이벤트도 확인했다. 124 인출에서 exact_capture 11회와 phash_same_layout
8회가 함께 있었으며, 전자는 빠른 갱신 경로다. 현재 코드가 픽셀 완전일치를 필수 조건으로
다시 강제했다고 해석할 근거는 없다. OCR 8.353초도 측정됐지만 예외 화면 관찰용으로 유지한
기능이므로 원격 호출 0회라는 이유만으로 불필요한 코드로 분류하지 않았다.

## 후속 작업의 범위

먼저 실제 기록으로 손실·예외가 확인된 1·2번과, 진단·후속 판단의 의미를 혼동시키는 3번을
다룬다. 4·5번은 합성 입력에서 경계를 확인했으므로 그 범위를 유지해 수정·검증한다.
6·7번은 동작을 유지하면서 제거할 수 있는 준비·변환의 정리로 분리한다.

현재 성공 경로에서 호출되지 않았다는 이유만으로 예외 복구나 검증 코드를 삭제하지 않는다.
728 passed, 3 xfailed는 이전 구현 검증 기록이며 이번 감사의 결과로 재표기하지 않았다.
이번 확인은 저장된 로그 집계, 원본 화면 확인, 실제 함수의 격리된 부분 재생이다.
새 ERP 실행·유료 호출·제품 변경은 수행하지 않았다.
