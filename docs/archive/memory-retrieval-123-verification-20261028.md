## 결론

시드 1의 새 탐색과 기억 인출 모두 ERP 10/10, 작업자 exit 0으로 끝났다.
기억 인출은 초반 5개 그룹·13개 행동을 원격 호출 없이 실행했다.
그러나 OCR 예외 복구 뒤 원본 절차로 충분히 복귀하지 못해 원격 호출 9회가 발생했다.
따라서 정상 구간의 무호출 실행은 확인했지만, 예외 복구 후 재사용까지 완성됐다고 볼 수 없다.

실행 중 제품 코드·프롬프트·설정은 변경하지 않았다. 재시도도 하지 않았다.

## 화면·원문으로 확인한 문제

### 1. 첫 예외는 값 입력 실패가 아니라 잘린 품명의 OCR 불일치였다

인출 프레임 `17aebc02-fa88-4e51-8afc-c43174345dca`에서 상단 품명 입력칸이 일부 잘려 있다.
`_restore_mapping`은 현재 OCR 문자열을 품명의 값으로 넣었다. seq 162 요청의
`screen.memory_fields`와 응답을 비교하면 요청의 OCR은 왜곡돼 있었고 모델은 정상 품명을 읽었다.
모델은 품명을 다시 입력하지 않고 예정된 하단 6개 입력을 동일한 좌표로 실행했다.
후속 상단 프레임에서도 품명 값이 정상적으로 보였다.

따라서 실제 입력 실패라는 해석은 맞지 않는다. 현재 코드의 관찰 불일치 예외는 작동했으며,
부분 노출 OCR을 신뢰할 수 없을 때 모델을 쓰는 사례 자체는 사용자 요구에 부합한다.
다만 이 예외 뒤 다음 기억으로 연결하는 처리까지 정상인 것은 아니었다.

### 2. 복구 후 이미 실행한 원본 그룹과 다음 그룹이 동시에 후보가 됐다

- seq 158: 원본 하단 입력 그룹 `376f8c199686240b` 결합.
- seq 162: 모델이 같은 행동·좌표로 복구 응답.
- seq 197: adaptation 그룹 `56891ec834b561c7` 전달 성공.
- seq 202–205: 다음 판단에서 원본 하단 입력과 후속 스크롤이 모두 후보여서 모델 호출.
- seq 226: 그 후에야 원본 그룹이 교체된 것으로 `method_edge_replaced` 기록.

`MemoryRetrieval.match_pattern`은 `unverified.replaced_edge`를 다음 그룹의 선행 조건
충족으로 인정하지만, 그 원본 그룹 자체는 아직 `used`가 아니어서 후보에서 제외하지 않는다.
원본 입력과 다음 스크롤이 둘 다 현재 캡처에 결합된다.

저장된 seq 205 화면/OCR·실행 이력·산출물로 무료 재생했다. 실제 이력에서 복원한 상태에서는
입력 그룹과 스크롤 그룹이 둘 다 결합되고 선택 결과가 None이었다. 격리된 반사실 상태에서
이미 전달된 원본 그룹만 used에 넣으면 스크롤 그룹 하나가 남아 정상 선택됐다.
제품 파일·원본 로그는 수정하지 않았다. 이 재생은 후속 전체 ERP 성공의 증거는 아니다.

이후 원본 스크롤 그룹은 모델 대체 경로로 진행됐지만 원본 그룹을 소비한 기록이 없었다.
후속 원본 그룹의 predecessor 제약 때문에 정상 인출로 복귀하지 못하는 방향과 일치한다.
후속 모든 no_unique 이벤트의 유일 원인을 같은 재생으로 증명한 것은 아니다.

### 3. 상세는 열렸으나 선택 후검증이 다음 행동을 중단했다

seq 332 모델은 결과 행 더블클릭에 `intent=select_option`, `source=hbl_no`를 지정했다.
프레임 `b4c6c6e1-b2f8-4ca6-a986-dd4773b47b41`에는 실제 House B/L 수정 창과 저장값이 보인다.
seq 358에서는 그 화면의 하단 스크롤 계획까지 받았다.
그러나 `_verify_selected_option`의 현재 관찰 대상 일치 조건이 실패하여 seq 371에
`selected_field_target_not_observed`가 남았고 다음 계획은 실행되지 않았다.
seq 380에서 다시 같은 화면을 판단한 뒤 스크롤했다.

이는 화면 이동 자체가 실패했다는 증거가 아니다. 선택 결과를 입력 필드 확인으로 다루는
후검증과 상세 이동 행동의 의미가 맞지 않은 경계다. 이번 검증에서 변경하지 않았다.

### 4. 완료 기억의 자동 결합은 아직 확인하지 못했다

편찬 completion은 현재 화면 대상 6개를 포함했지만 최종 완료 결합 이벤트는 0건이다.
남아 있는 원본 그룹 때문에 completion 분기의 `not remaining`에 도달하지 못했다.
최종 프레임 `61b959c3-23d0-40a6-a4dd-b1daa497c30f`에는 수정 창의 하단 저장값이 보이며,
seq 414–415의 기존 저장 후 누적 증거 검토가 성공을 선언했다.
완료 계약을 저장했다는 확인과 실제 인출 종료에서 사용했다는 확인을 혼동하면 안 된다.

## 검증의 범위와 반증 조건

- 실제 Windows Mock ERP 창을 조작했고 로그인·등록·스크롤·저장 후 상세 캡처를 직접 검토했다.
- ERP 독립 채점과 작업자 정상 종료를 모두 확인했다. 실행 중 제품 수정이나 반복 재시도는 없다.
- 정상 5개 그룹에서 원격 호출 0회는 로그로 확인한 사실이다. 다른 시드에도 성립한다고 일반화하지 않는다.
- 복구 그룹과 원본 그룹의 행동·입력 키·좌표가 다르거나, 해당 시점 원본이 이미 used였다면
  후보 중복 진단은 틀리다. 이번 기록에서는 동일 행동이고 원본 소비 이벤트는 후속 판단 뒤였다.
- 원본 그룹 소비만 바꾼 무료 재생으로 후보 충돌은 해소됐지만 전체 절차 복귀와 최종 완료는
  다음 변경 이후 새 ERP 검증이 필요하다. 이번에는 수정하거나 추가 유료 실행하지 않았다.
- 전체 단위 테스트는 재실행하지 않았다. 이번 변경은 보고서와 비공개 계측·분석 산출물뿐이다.
  실행한 제품 커밋의 직전 검증은 727 passed, 3 xfailed였으며 실제 ERP 결과와 별개다.

다음 수정 후보는 복구 완료 그룹의 소비 시점과 후보 제외를 일치시키는 것이다.
OCR 예외를 없애거나 허용 횟수를 늘리는 것으로 이번 후보 충돌을 해결할 근거는 없다.
