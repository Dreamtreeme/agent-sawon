# 파일럿 판단과 화면 전이 비교

대상 실행은 `completion-latch-pilot-20261010-004`이다. 비교 기준은 각 판단 직전 캡처,
실제 전송된 입력, 다음 관찰 캡처다. 노란 원은 실행 좌표이며 왼쪽은 판단 직전, 오른쪽은
다음 관찰이다.

`Decision.reason`은 현재 화면을 설명하는 필드가 아니다. `compile_match()`가 모델 응답의
`expected_result`를 그대로 옮기므로, 화면에 아직 없는 결과가 현재형 문장으로 기록될 수 있다.
따라서 아래 평가는 `subgoal/action`을 의도, `reason`을 기대 후조건으로 해석했다.

17개 판단 묶음 중 13개는 기대한 상태로 갔다. 재조회 1개는 완전 중복이고, 저장 안내 닫기
1개는 기대 후조건이 너무 넓었으며, 상세 열기 2개는 올바른 좌표에 잘못된 제스처를 반복했다.
좌표 보완 판단은 좌표가 정상이라고 진단했고, 그 다음 더블클릭이 성공했다.

호출은 화면 전이마다 한 번씩만 발생하지 않았다. 로그인, 최초 조회, 저장에서 각각 3회가
사용됐고 신규 등록과 추가정보 탭에서 각각 2회가 사용됐다. 이 다섯 판단 묶음이 13회,
나머지 12개 판단이 12회를 사용해 총 25회다.

## 1. 로그인

판단은 계정과 비밀번호를 입력하고 로그인 버튼을 클릭하는 3행동 배치였다. 실제로 메뉴
화면에 도달했다. 다만 이 성공 계획을 만들기 전에 모델이 쓰기 불가능한 OCR 텍스트 표면을
두 번 골라 교정 호출이 발생했다.

Haiku는 `seq 5 → 11 → 15`에서 3회 사용됐고 마지막 호출이 실제 배치 계획을 만들었다.

![로그인 판단과 화면 전이](assets/pilot-decision-trace-20261010/01-login.png)

## 2. 조회 메뉴 열기

`House B/L 조회` 버튼을 선택했고 빈 조회 화면으로 전환됐다. 판단과 실제 전이가 일치한다.
로그의 “House B/L 번호 입력 칸과 조회 버튼이 보인다”는 현재 메뉴 화면 설명이 아니라 클릭
후 기대 결과다.

Haiku는 `seq 38`에서 1회 사용됐다.

![조회 메뉴 판단과 화면 전이](assets/pilot-decision-trace-20261010/02-open-query.png)

## 3. HBL 번호 입력

화면 매칭이 `hbl_no`를 상단 입력칸에 연결했고 코드가 값을 입력했다. 다른 업무 버튼을 누르지
않고 동일 조회 화면에서 값만 바뀌었다.

Haiku는 `seq 57`에서 1회 사용됐다.

![HBL 입력 판단과 화면 전이](assets/pilot-decision-trace-20261010/03-fill-hbl.png)

## 4. 최초 조회

입력된 HBL 증거와 조회 버튼을 선택해 실행했다. 다음 화면에 `조회 결과 0건`이 나타났으므로
행동 효과는 정확했다.

Haiku는 `seq 74 → 84 → 88`에서 3회 사용됐다. 첫 호출은 값 후검토, 두 번째는 조회 계획,
세 번째는 버튼 target 교정이다.

![최초 조회 판단과 화면 전이](assets/pilot-decision-trace-20261010/04-search-first.png)

## 5. 불필요한 재조회

이미 `조회 결과 0건`이 보였지만 모델이 같은 조회 버튼을 다시 선택했다. 전후 screen hash는
모두 `3093498b...`로 완전히 같다. 이 판단은 새 정보를 만들지 않은 명백한 중복이다.

Haiku는 `seq 103`에서 1회 사용됐으며 호출 전체가 불필요한 재조회로 이어졌다.

![재조회 판단과 동일 화면](assets/pilot-decision-trace-20261010/05-search-repeat.png)

## 6. 신규 등록 열기

두 번째 판단에서는 0건을 인정하고 `새 건 등록`을 선택했다. 신규 기본정보 화면이 열렸다.

Haiku는 `seq 122 → 126`에서 2회 사용됐다. 두 번째 호출은 신규 버튼 표면만 다시 접지했다.

![신규 등록 판단과 화면 전이](assets/pilot-decision-trace-20261010/06-open-new.png)

## 7. 기본정보 배치 입력

HBL, MBL, 수출자, 수하인, 화물 내역 5개 값을 한 화면 판단에서 연결한 뒤 연속 입력했다.
다음 관찰에서 5개 값이 모두 보였다.

Haiku는 `seq 141`에서 1회 사용됐다.

![기본정보 배치 입력과 화면 전이](assets/pilot-decision-trace-20261010/07-fill-main.png)

## 8. 추가정보 탭 열기

기본정보가 채워진 뒤 추가정보 탭을 눌렀고 6개 입력칸이 있는 화면으로 이동했다. 로그의
reason은 탭을 누른 뒤의 기대 화면을 현재형으로 기록한다.

Haiku는 `seq 168 → 182`에서 2회 사용됐다. 값 후검토와 다음 행동 계획이 분리돼 있었다.

![추가정보 탭 판단과 화면 전이](assets/pilot-decision-trace-20261010/08-open-additional.png)

## 9. 추가정보 배치 입력

포장 수량·단위, 총중량, 컨테이너 번호, POL, POD 6개 값을 한 번에 매칭해 연속 입력했다.
다음 관찰에서 6개 값이 모두 채워졌다.

Haiku는 `seq 197`에서 1회 사용됐다.

![추가정보 배치 입력과 화면 전이](assets/pilot-decision-trace-20261010/09-fill-additional.png)

## 10. 저장

현재 6개 추가정보 증거를 붙여 저장 버튼을 선택했다. 다음 화면에 HBL 번호와 저장 번호가
포함된 저장 완료 대화상자가 나타났다.

Haiku는 `seq 225 → 228 → 240`에서 3회 사용됐다. 후검토 뒤 첫 저장 계획이 target 불일치로
반려됐고, 마지막 호출이 전체 화면을 다시 판단해 저장 버튼을 선택했다.

![저장 판단과 화면 전이](assets/pilot-decision-trace-20261010/10-save.png)

## 11. 저장 안내 닫기

확인 버튼 자체는 올바르게 눌렀다. 그러나 판단의 기대 결과는 “안내가 닫히고 조회 화면으로
이동”이었고, 실제로는 안내만 닫혀 저장된 편집 화면으로 돌아왔다. 하나의 클릭에 두 단계
후조건을 부여한 것이 문제다.

Haiku는 `seq 257`에서 1회 사용됐다.

![저장 안내 닫기 판단과 화면 전이](assets/pilot-decision-trace-20261010/11-close-dialog.png)

## 12. 조회 화면으로 복귀

편집 화면의 닫기 버튼을 누르자 저장된 행이 보이는 조회 결과 화면으로 돌아왔다. 11번의
누락된 두 번째 전이를 별도 판단으로 수행한 셈이다.

Haiku는 `seq 275`에서 1회 사용됐다.

![조회 복귀 판단과 화면 전이](assets/pilot-decision-trace-20261010/12-return-query.png)

![상세 열기 1차 판단과 화면 전이](assets/pilot-decision-trace-20261010/13-open-detail-click-1.png)

전이도 일어나지 않았다. 첫 실패의 효과를 다음 선택 제약으로 쓰지 못해 같은 제스처를 반복했다.

## 15. 좌표 상세 검토

보완 호출은 클릭 좌표가 실제 결과 행 내부라고 판정했다. 화면은 그대로였고 입력도 보내지
않았다. 이 판단은 문제를 좌표 오차가 아니라 제스처 선택으로 좁혔다는 점에서 맞다.

Haiku는 `seq 328`에서 1회 사용됐다. 이 호출은 25회 중 유일한 작은 이미지 좌표 검토다.

![좌표 상세 검토와 동일 화면](assets/pilot-decision-trace-20261010/15-coordinate-review.png)

Haiku는 `seq 335`에서 1회 사용됐다.

![상세 열기 더블클릭 판단과 화면 전이](assets/pilot-decision-trace-20261010/16-open-detail-double.png)

## 17. 완료

현재 상세 화면의 기본정보 5개와 앞서 검증해 누적한 추가정보 6개를 결합해 `complete`를
반환했다. 추가 클릭 없이 `task_completed_with_verified_evidence`로 종료했다.

Haiku는 `seq 348`에서 1회 사용됐다.

## 결론

이번 실행의 주된 문제는 좌표 탐지가 아니다. 입력 필드 12개와 버튼·탭·행 좌표는 모두 실제
대상에 들어갔다. 낭비는 화면 효과를 다음 판단에 전달하는 방식에서 생겼다.

1. 최초 조회 결과의 `0건`을 바로 다음 단계 조건으로 소비하지 않아 조회를 한 번 반복했다.
2. 저장 안내 확인 한 번으로 조회 화면까지 갈 것이라는 두 단계 후조건을 만들었다.
3. 행 단일 클릭의 실제 효과가 “선택됨”이었는데도 같은 제스처를 다시 허용했다.
4. `reason`이 현재 관찰처럼 보이지만 실제로는 `expected_result`라서 로그 해석을 혼란시킨다.

따라서 다음 수정의 핵심은 새 좌표 휴리스틱을 추가하는 것이 아니라, 판단 로그에서 현재 증거와
기대 후조건을 분리하고, 실제 행동 효과를 다음 선택에 넣어 동일 화면·동일 제스처의 반복을 막는
것이다.
