## 현재 공통 실행 구조

```mermaid
flowchart TD
    D[서류 추출·교차 검증] --> RECORD[ShipmentRecord]
    RECORD --> O[Observe: relay 관찰·시각 분석]
    O --> R[Review: 현재 업무 근거]
    R --> S[Select: 모델·캐시·로그인/등록 계획]
    S --> P[ActionPlan: 행동 목록·검증 종류]
    P --> PR[Review: 판단 evidence 저장·실행 전 검토]
    PR -->|완료| F
    PR -->|계속| A[Act: 공통 execute_plan]
    A --> G[전체 계획의 정책·대상·단계 한도 검사]
    G --> X[공통 dispatch·좌표 갱신·relay 입력·기록]
    X -->|같은 화면의 다음 행동| X
    X -->|묶음 완료| V[Verify: 새 화면 한 번 관찰]
    V --> K[결과별 검증: 로그인 전환·필드 값·조회 근거]
    K --> F[공통 증거 기록·transition 기록]
    F -->|시각 관찰 재사용| R
    F -->|UIA 현재 상태 재확인| O
    K -->|실패| B[기존 실패 정책·복구 한도]
    B --> O
```

`screen_batch`는 모델 응답을 공통 계획으로 변환하고, 필드 묶음의 결과를 해석한다.
직접 relay 입력을 보내거나 전체 인식을 시작하지 않는다. `execution`은 계획의 입력 순서와
전달 기록을 관리한다. `engine`은 그래프·업무 단계·관찰과 검증의 연결을 담당한다.
로그인/등록/조회는 결과의 의미가 다르므로 하나의 성공 조건으로 합치지 않는다.

시각 단일 행동도 검증 장면을 다음 판단에 재사용한다. UIA는 다음 선택 전의 저비용 관찰을
유지한다. 기존 관찰 후 조회값 변경을 검출하는 동작까지 무조건 생략하면 안 되므로,
관찰 방식에 필요한 최신성 차이는 유지한다. 두 경로의 행동 실행기는 동일하다.

텍스트/이미지 비용 예약과 비용 합산은 모델 계층의 공통 기능이다. 모델 계층은 두뇌나
서류 처리 구현을 import하지 않으며 공개 이벤트와 이미지 크기 프로토콜만 받는다.
서류의 단위 변환·증빙 대조와 UI 값 비교는 의미가 달라 별도로 유지한다.

## 후속 수정 · 입력 영역과 저장 결과

- `observe.evidence.is_record_input`을 공통 기준으로 사용한다. 현재의 평면 ShipmentRecord
  필드는 form의 edit/combobox이며, table/list/row 내부의 반복 품목 칸은 대응 대상이 아니다.
  단일/묶음 실행, 검증 사실 기록, 캐시/시연 후보가 같은 기준을 사용한다. 이름·좌표로 판정하지 않는다.
  일반 레코드를 표 형태로 편집하는 다른 앱까지 지원한다는 의미는 아니다. 그런 앱에는
  레코드/반복행 소속을 구분하는 별도 계약 확장이 필요하다.
- 저장 클릭 전달은 `save_result` 단계로만 전환한다. 다음 선택 응답 SaveReviewResponse에서
  현재 화면 근거 ref와 결과, 다음 행동을 함께 받는다. 별도 결과 분류 API 호출을 추가하지 않는다.
  거절이면 enter로 돌아가 지적된 필드의 검증만 해제하고 오류창 처리 후 다시 계획한다.
  확인창이면 confirm_save를 실행하고 save_result에서 결과를 다시 판단한다.
  ready_for_query만 final_query로 전환하며 이것은 저장 성공 확정이 아니다.
  최종 성공은 기존의 새 조회·같은 행 전체 값 증거로만 판정한다.
- 현재 계약으로 고칠 수 없는 반복 품목 오류는 임의 품목 값을 만들지 않고 중단한다.
  알 수 없는 저장 결과/오래된 근거도 성공 또는 재조회 단계로 넘어가지 않는다.
  결과와 지적 필드의 의미 해석은 모델의 판단이므로 실제 모델에서의 정확성 검증은 남는다.
- 저장된 실제013 관찰 재생: 잘못 선택한 표 셀2개는 거절, 정상 등록 입력6개는 허용했다.
  새 모델 호출·화면 행동 없이 확인한 구조 검증이며 실제 전체 업무 성공률은 아니다.
- OCR/탐지 worker 재로딩은 별도 성능 작업으로 남는다. 다음 단계는 변경된 결과 응답을 포함한
  제한된 실제 파일럿이다. 이 수정 작업에서 화면 실행을 재개하지는 않았다.

## 로컬 OCR·탐지 모델 수명 관리 · 2026-09-30

`PersistentWorker`와 stdlib 전용 `worker_server`를 OCR/탐지가 공유한다.
요청은 입력 파일 경로를 전달하고 결과는 요청별 파일을 원자적으로 교체해 받는다.
모델 라이브러리의 stdout/stderr는 프로토콜과 분리한다. 화면 캐시가 아니라 모델 인스턴스를
유지하는 구조이며 이미지가 바뀔 때마다 새 추론 결과를 얻는다.

- OCR worker의 OcrSession은 설정이 같으면 PaddleOCR 인스턴스를 재사용한다.
  YOLO worker의 DetectorSession은 같은 weights에서 기본/보완 탐지를 함께 처리한다.
- 실패 요청은 같은 요청을 몰래 재시도하지 않는다. 해당 프로세스/소유 자식을 종료하고
  다음 요청 때 새 프로세스/모델로 시작한다. timeout도 같은 공통 정리를 사용한다.
- Brain.run의 finally, 시각 기록 CLI의 finally, 서류 준비의 자체 소유 OCR 정리에서 close한다.
  외부 주입 OCR은 서류 호출자가 소유한다. 정상 인터프리터 종료에도 atexit으로 정리한다.
  강제 종료는 부모 harness의 소유 프로세스 트리 종료가 담당한다.
- 첫 요청/재사용별 PID·model_initialized·model_init_ms·inference_ms·round_trip_ms를 기록한다.
  공개 wire 계약, 모델 측정 래퍼, 유료 예산, 화면 좌표 바인딩은 변경하지 않았다.
- 저장된 로그인/메뉴 이미지만 사용한 로컬 진단001: OCR7.01→6.53초, 기본 탐지4.74→0.91초.
  이미지가 다르므로 동일 작업 속도 향상률로 계산하지 않는다. 각 worker의 PID는 동일하며
  두 번째 요청의 초기화 시간은0이다.
- 진단002는 로그인→메뉴→로그인→메뉴 순서로 같은 worker를 유지했다. 동일 로그인의

## GPU 실행 전환 · 2026-09-30

사용자가 L2C처럼 GPU 실행을 요청했다. 기존 코어 Paddle은 CPU 빌드였고 YOLO worker는
device를 CPU로 고정했다. 이 컴퓨터에는 RTX3080과 L2C GPU 환경이 이미 설치되어 있었다.
현재 네 OCR 프로필은 `gpu:0`과 L2C `.venv-ocr`를 명시하며 visual 탐지는 `cuda:0`을
전달한다. 기본/보완 탐지는 같은 장치를 사용한다. 설정 없이 생성하는 라이브러리 기본값은
CPU를 유지하며 실제 실행 프로필이 GPU를 선택한다. CPU로 자동 대체하지 않는다.

OCR 격리 환경의 CUDA/cuDNN DLL을 import 전에 등록한다. Python3.13.14,
PaddlePaddle GPU3.3.1/CUDA13, PaddleOCR3.7.0, PaddleX3.7.2이며 CUDA 빌드/장치1개를
확인했다. YOLO는 L2C의 torch2.13.0+cu130을 사용하고 predictor 장치 `cuda:0`을 기록했다.

저장된 로그인622×476/메뉴782×566을 GPU와 CPU 각각 같은 환경에서 교대로 읽었다.
한국어 프로필의 두 번째 로그인은 OCR CPU2.024초→GPU0.091초, 메뉴는3.832초→0.133초였다.
같은 시점 탐지는 로그인0.272초→0.061초, 메뉴0.229초→0.064초였다.
GPU 첫 요청은 한국어 OCR4.89초/탐지5.19초였고, 앞선 영어 실험 첫 OCR은18.70초였다.
초기화/첫 추론 비용은 사라지지 않으므로 후속 요청 수치와 분리한다. 전용 성능 환경이나
반복 평균은 아니며 회귀 테스트는 측정 종료 후 시작했다.

한국어 결과는 모든 CPU/GPU 대응 화면의 문자 목록이 같았고, 로그인 좌표는 최대1px 차이,
메뉴 좌표는 동일했다. 영어 프로필에서는 로그인 문자 블록1개의 문자열이 달랐다.
같은 블록 수/속도만으로 인식 정확도가 동일하다고 주장하지 않는다.
근거: cases/gpu-visual-20260930-002(영어),003(한국어)의 measurement/verification.json.
001은 진단 스크립트 로그 생성 인자 오류로 모델 실행 전에 종료했다. 모든 측정 worker의
종료와 잔존0을 확인했다. API 호출0/ERP 행동0이며 기존 비용과 미확정 호출은 유지한다.

## 생산 코드 재사용 통합 · 2026-10-01

사용자의 `계획실행` 요청으로 재사용 점검의 우선 6항목을 구현했다. 새 화면 실행이나
유료 호출은 하지 않으며, 기존 테스트와 합성 회귀로 공통 계약을 검증한다.

| 책임 | 공통 경계 | 유지한 차이 |
| --- | --- | --- |
| 레코드 값 동등성 | `observe.values.values_for/field_matches`를 cache/demo에서도 사용 | 캐시 label 정규화·변경 전후 증거·승격 조건 |
| 최종 조회 선행 조건 | `ExecutionFacts.final_query_workflow_ready` | 실제 row/field 증거·saved session 조건은 각 경계에서 추가 검증 |
| 결과 행 필드 배정 | `review.assign_result_fields` | review의 진단과 SavedEvidence의 관측 연결·충돌 관리 |
| 화면 해석/재해석 | `SemanticRequest`와 `VisualPerception._resolve/rematch` | 새 화면은 캡처/OCR/기본 탐지, 동일 화면은 기존 후보 재사용 |
| 비용·schema·OCR 규칙 | 기존 `read_model_accounting`, `compact_provider_schema`, `validate_ocr_blocks/limits` | 실제 비용 한도 정책, 로컬 schema 제한, 개별 view/합산 검증 시점 |
| 벤치 채점 입력 | `grader.io`의 strict JSON 및 ERP export 읽기 | CLI 출력·종료 코드, 사람 실행의 완료 조건, 하네스 실행 정책 |
| 벤치 행동 결과 | `RelayService._execute_action` | UIA/visual 대상·입력·실패 후 screenshot 옵션 |

ScreenMatch는 프롬프트 문자열에서 JSON을 다시 찾지 않는다. perception이 화면 후보와
교정 정보를 `SemanticRequest`로 전달하고, 모델 호출 직전에만 필요한 프롬프트로 만든다.
같은 화면의 재해석도 공통 grounding·제한된 correction/refinement·검증된 detection 갱신을
거친다. rematch 때문에 캡처·OCR·기본 탐지를 반복하지 않는다. 보완을 소진한 오류는
observe/verify/select 어디에서든 종료되어 바깥 선택 루프가 보완 횟수를 다시 만들지 않는다.

`_workflow_facts`는 관측 증거 review를 호출하지 않으므로 policy와 review가 서로 재귀하지
않는다. 조건을 공통 함수로 모아도 실제 실행·완료 경계에서의 검사는 계속 수행한다.
단일·로그인·필드 묶음은 기존 `ActionPlan → execute_plan → act → verify`를 유지한다.

벤치는 부가적으로 matrix/notebook의 외부 예외를 `uncertain_failure_row`로 연결하여,
시작 여부를 모르는 실행을 미시작으로 기록하던 차이를 제거했다. Core와 bench의 구현은
서로 import하지 않는다. HTTP transport·파일 저장 기반 전면 통합과 가격 정책 재설계는
이번 6항목 범위에 포함하지 않았다.

공통 export decoder는 한 번 읽은 원본에서 shipment의 숫자 타입·Decimal 정밀도를 보존한
내부 identity도 만든다. 저장 전후 비교는 현재 모델 비교와 원본 identity를 함께 사용한다.
이렇게 지수형 중량의 채점은 통일하면서, float 변환이 미세 변경을 지우는 회귀를 막는다.
identity는 공개 export schema에 추가되지 않으며 JSON 공백/객체 key 순서는 무시한다.

최종 검사 수와 실행 결과는 bench `docs/progress.md`의 같은 날짜 구현 기록에 남긴다.

## 2026-10-02 클릭 좌표와 업무 순서의 소유권

녹화 파일럿018–021은 실행기가 모델의 세부 시각 판단을 후보 중심점으로 축약하고, 넓은
`fill-entry` 단계가 작업자 모델에 전체 미완료 필드의 순서 결정을 맡긴다는 두 결합을 드러냈다.
클릭 실패 뒤 좌표를 한 번 더 묻는 것만으로는 다음 모델 호출의 절차 재해석을 막지 못한다.

현재 `ScreenMatch` 클릭은 원본 이미지의 점을 필수로 반환한다. `VisualPointBindings`가 이를
현재 observation/ref/action/intent에 묶고 후보 사각형 내부인지 확인하며, 실행기는 그 점을
그대로 relay에 보낸다. 일반 Decision/Choice와 의미 캐시에는 좌표를 넣지 않는다.

절차 단계는 `view`, `field_scope`, `requires_verified`로 사용자가 가르친 업무 그래프를 표현한다.
런타임은 선행조건과 현재 미완료 필드로 후보 단계를 줄이고 선택된 단계 밖의 필드 행동을
거절한다. 모델은 화면과 단계의 대상을 연결하며 필드 처리 순서를 새로 설계하지 않는다.
ERP 라벨, 좌표, AutomationId, 탭 순서는 코드에 넣지 않는다.

다음 분리 경계는 화면 의미 해석과 행동 계획이다. 화면 내용/마커 지문에 연결한 역할·관계만
재사용하고, 업무 값·단계·행동·과거 좌표는 매 관찰의 현재 계약으로 다시 결합해야 한다.

이 경계를 `SemanticDetection`과 `ScreenPlan` 두 호출로 구현했다. 관찰 호출은 업무 절차나
행동을 반환하지 않고 화면 종류와 컨트롤 의미만 분류한다. 로컬 grounding 성공 뒤 이미지
SHA-256·창 geometry별 catalog에 저장하며 A→B→A 재방문도 최대 16개 화면까지 재사용한다.
입력 검증으로 중앙 상태를 갱신한 다음에만 선택 호출이 현재 절차·notebook과 고정된 의미를 받아
행동과 클릭점을 반환한다. 픽셀이 달라지면 새 의미 인식을 하며 과거 행동·ref·좌표는 보관하지 않는다.

### 외부 선택 결과의 필드 효과

화면 클릭 Decision은 provider 정책상 레코드 source를 갖지 않으므로, `ScreenMatch`의
select_option source를 버리면 ERP에 값이 반영돼도 중앙 상태가 알 수 없다. 선택형 ActionPlan은
마지막 적용 클릭의 source를 별도 `effect_source`로 보존한다. 조회 진입 전 편집 칸 descriptor와
복귀 후 현재 값을 대조해 일치할 때만 field verification을 기록한다. 이 사후조건이 실패하면
같은 조회를 반복하지 않고 명시적으로 중단한다.
