# OmniParser v2 전환 및 실제 화면 검증 — 2026-10-08

사용자 요청: 다음 실행 전에 OmniParser v2로 전환한다. 기존 레거시 삭제 후보는
이번 변경에 포함하지 않았다. Luna, 시드19의 회사 교육·합성 업무 입력, 결합 화면 판단,
빈 캐시·방법 저장소를 직전 성공과 동일하게 유지했다. 실행당 비용 상한은 $1이며
기존 총 $50 승인 범위다. 평가 시드는 사용하지 않았다.

## 기존 상태 정정

기존 L2C의 `icon_detect/model.pt` SHA-256은
`dab3d4351ad00b035db829909a4db98354d5a90f6990e4ac00222a9a95d4bf57`이다.
공식 microsoft/OmniParser-v2.0의 icon_detect와 동일하다. 따라서 과거 기록의
“v1 탐지 가중치”는 부정확했고, 정확한 비교는 **v2 탐지 전용 → v2 탐지 + 캡션**이다.
기존 기본 설정의 v2 경로는 존재하지 않는 폴더를 가리켰다. 과거 파일럿은 실제 존재하는
탐지 가중치를 사용하고 캡션을 껐다.

## 구현

- `data/models/omniparser-v2`에 공식 탐지·캡션 자산과 Florence processor/custom code를 준비했다.
  자산 revision과 로컬 auto_map 정규화는 해당 폴더의 `source.json`에 보관한다.
- 기존 OCR 환경은 유지하고 `.tools/vision-venv`를 별도로 만들었다. torch2.13.0+cu130,
  torchvision0.28.0+cu130, transformers4.49.0, timm1.0.30, einops0.8.2를 사용한다.
- YOLO와 Florence는 동일한 persistent GPU worker에서 재사용한다. Florence는 FP16,
  64×64 crop, batch16, greedy 생성이며 텍스트 전용 attention_mask는 전달하지 않는다.
- 기존 OCR 상자를 일반 관찰·행동 재결합·보완 탐지에 전달한다. OCR와 겹치는 텍스트는
  캡션 대상에서 제외한다. OCR나 캡션 결과를 업무 완료 증거로 자동 승격하지 않는다.
- 누락된 캡션 파일이나 추론 실패를 조용히 탐지 전용 성공으로 바꾸던 처리를 제거했다.
  model_init/caption_init/detection/caption 시간, OCR 제외 수와 생성 수를 계측한다.
- 전체 화면의 `image_size`는 캡션 활성화와 독립된 설정이다. 현재640이며 보완 crop은1280이다.
  원본 이미지 좌표로 변환하는 기존 계약을 유지한다.

참조: [공식 v2 자산](https://huggingface.co/microsoft/OmniParser-v2.0),
[공식 Florence 배치 구현](https://github.com/microsoft/OmniParser/blob/master/util/utils.py).
다운로드 자산, 격리 환경, 화면/프롬프트/캐시 원본은 Git에 포함하지 않는다.

## 무료 캡처 검증과 발견된 회귀

저장된 실제 로그인·등록 캡처에서 GPU 초기화 및 다음 화면 재사용을 확인했다.
초기 실측(1280 탐지)에서 등록 화면은57개 탐지 중 OCR 영역47개를 제외하고10개만 캡션했다.
탐지141.6ms + 캡션290.7ms =432.3ms이며, 두 번째 화면에서 모델 초기화는0회였다.
OCR 제외 전 같은 화면의 탐지+캡션은1311.8ms였다. 이는 캡처별 단일 측정이며
전체 ERP 처리시간이나 모든 화면에서의 속도를 뜻하지 않는다.

배치 통합 중 Florence의 텍스트 전용 attention_mask를 함께 전달해 토큰 길이가
맞지 않는 오류를 발견했다. 공식 구현처럼 input_ids/pixel_values만 전달해 해결했다.
이 오류는 이번 구현 검증에서 발생한 것이며 과거 파일럿 실패 원인으로 소급하지 않는다.

첫 유료 실행 `core-pilot-20261008-144358-omniparser-v2`는 새 전체 탐지 크기1280에서
긴 조회 입력칸을 놓쳤다. 영상의 빈 입력칸은 계속 보였지만 마커 목록에는 없었다.
모델은 OCR 라벨8번을 입력 대상으로 제안했고 seq52/58/80/86에서 입력 가능한 대상이
아니어서 보완 처리됐다. 빈 조회 클릭 후에도 입력칸은 비어 있었다. 최종 종료는
seq94/95 `visual_grounding:ocr_marker_text_mismatch`다. ERP 저장은0/10이다.

같은 실패 캡처·같은 가중치·같은 confidence0.15를 고정한 무료 비교:

| 전체 탐지 크기 | 긴 빈 조회 입력칸 | 탐지 상자 수 |
|---|---|---:|
| 1280 | 누락 | 48 |
| 640 | `[178,66,913,49]`, confidence0.4721 | 50 |
| 640 + Florence 활성 | 동일 좌표·confidence | 50 |

따라서 이번에 v2 캡션과 함께 전체 탐지 크기를 바꾼 것이 조회 입력칸 회귀의 직접 원인이다.
640이 모든 화면에서 더 우수하다는 뜻은 아니다. 이전 성공 설정640을 보존하고,
캡션 활성화가 탐지 해상도를 암묵적으로 바꾸지 않도록 분리했다. 입력 가능성 검사를
삭제하거나 특정 ERP 좌표/라벨을 하드코딩하지 않았다.

캡션 자체의 정확성에는 한계가 있다. 빈 입력칸에 `Increase`, `Center`처럼 화면 기능과
맞지 않는 설명을 만들었다. 따라서 캡션 추가만으로 정확도나 업무 성공이 개선됐다고
판정할 수 없다. 현재 화면 OCR·이미지와 Luna 판단의 보조 정보로만 사용한다.
